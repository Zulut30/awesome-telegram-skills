# ЮKassa

Выбери маршрут: Telegram provider invoice для допустимого товара либо прямая backend-интеграция через API ЮKassa. Токен провайдера от BotFather и shop secret ЮKassa используются в разных маршрутах. Прочитай [references/yookassa.md](references/yookassa.md), проверь требования товара и магазина.

Для прямого API создай серверный заказ, payment attempt и устойчивый ключ идемпотентности. Получай подтверждение платежа от сервера провайдера; frontend confirmation/return URL отвечает за UX. Передавай локальный order ID в metadata для сверки, не устанавливай его по callback без проверки.

Используй Decimal/строковую сумму согласно API. Согласуй immediate capture либо двухстадийную оплату с продуктом. `waiting_for_capture` не означает окончательное списание; выдача товара должна следовать выбранной модели платежа.

Подлинность входящего уведомления проверяй способом ЮKassa, а не придуманным общим HMAC. Для критического перехода прочитай платеж/возврат своим серверным API-клиентом, сопоставь состояние, сумму, валюту и metadata с заказом. IP validation за proxy требует корректной модели доверия к заголовкам.

Транзакционный переход и outbox защищают выдачу от повторов. Обработка не должна зависеть от единственного webhook; сверяй незавершенные attempts. Для sync SDK в async backend используй ограниченный управляемый executor либо HTTP adapter.

Для возврата, сохраненного способа оплаты, рекуррентного списания и чека прочитай документацию соответствующей функции. Данные магазина, способ расчетов и настройки чеков нужно подтвердить; не придумывай налоговые параметры по общему шаблону.

Проверь тестовый магазин, повтор POST с тем же ключом, forged callback, capture, отмену, возврат и повтор подтвержденного события по релевантности. Раздели synthetic и provider sandbox evidence.
