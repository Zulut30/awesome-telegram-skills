# ЮKassa

Выберите маршрут: счет Telegram через платежного провайдера (provider invoice) для допустимого товара либо прямую серверную интеграцию с API ЮKassa. Токен провайдера из BotFather и секретный ключ магазина ЮKassa используются в разных маршрутах. Прочитайте [references/yookassa.md](references/yookassa.md) и проверьте требования к товару и магазину.

Для прямого API создайте серверный заказ, попытку оплаты и устойчивый ключ идемпотентности (`Idempotence-Key`: повтор запроса с тем же ключом не создает второй платеж). Подтверждение платежа получайте от сервера провайдера; страница подтверждения и возврата пользователя отвечает только за удобство. Передавайте локальный ID заказа в `metadata` для сверки (запроса фактического статуса платежа) и не меняйте его по уведомлению без проверки.

Сумму передавайте как `Decimal` или строку, как требует API. Согласуйте с продуктом немедленное списание или двухстадийную оплату (сначала блокировка средств, затем подтверждение). `waiting_for_capture` не означает окончательного списания; выдача товара следует выбранной модели платежа.

Подлинность входящего уведомления проверяйте способом ЮKassa, а не придуманной общей HMAC-подписью. Перед переходом, от которого зависит выдача, запросите платеж или возврат своим серверным API-клиентом и сверьте статус, сумму, валюту и `metadata` с заказом. Проверка IP-адреса за прокси требует корректно настроенного доверия к заголовкам.

Повторную выдачу предотвращают транзакционный переход заказа и outbox — запись о событии в той же транзакции, которую выполняет отдельный обработчик. Обработка не должна зависеть от единственного уведомления: периодически сверяйте незавершенные попытки. Синхронный SDK в асинхронном сервере вызывайте через ограниченный пул потоков либо замените прямыми HTTP-запросами.

Для возврата, сохраненного способа оплаты, рекуррентного списания и чека прочитайте документацию соответствующей функции. Данные магазина, систему налогообложения и настройки чеков подтвердите у владельца магазина; не выдумывайте налоговые параметры по общему шаблону.

Проверьте в тестовом магазине повтор запроса создания с тем же ключом, поддельное уведомление, подтверждение двухстадийного платежа, отмену, возврат и повторное подтвержденное событие — то, что относится к задаче. Отделяйте синтетические проверки от проверок в тестовой среде провайдера.
