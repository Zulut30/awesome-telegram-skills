# Адаптеры внешних платежей

Термины: квитанция (receipt) — сохраненная запись о выполненной операции; повтор возвращает ее вместо второго эффекта; **неизвестный результат** — запрос мог выполниться, но ответа нет (таймаут, обрыв связи); повторять вслепую нельзя, сначала сверка; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

`telegram_patterns.providers` содержит необязательные адаптеры `CryptoPayAdapter`,
`PlategaAdapter` и `YooKassaAdapter`. Они используют стандартную библиотеку Python и
переданный приложением асинхронный HTTP-транспорт. Импорт не открывает соединений и
не требует SDK провайдера. Это локальная подготовка пунктов 75–77: кабинетов,
ключей, тестовых магазинов и настоящих платежей при разработке не было.

Адаптер не выбирает законный маршрут оплаты. Для цифровых товаров и услуг внутри
Telegram по-прежнему нужны Stars; наличие внешнего адаптера само по себе не
разрешает внешний платежный сценарий. Отдельный обзор маршрута из пункта 71,
договор магазина и налоговые требования остаются обязательной частью внедрения.
[Правила Telegram для цифровых товаров](https://core.telegram.org/bots/payments-stars)

## Общий контракт

`InvoiceRequest(binding, description, return_url, expires_in=900)` получает
`PaymentBinding` из неизменяемого серверного заказа. Идентификаторы продавца,
бота, покупателя, заказа, провайдера, сумма, валюта и политика возврата не берутся
из клиентского уведомления. `binding_reference(binding, operation_id)` вычисляет
непрозрачный SHA-256 от полной привязки и устойчивого идентификатора операции.
Это ссылка для сравнения, а не секрет и не доказательство подлинности.
`expires_in` передается только Crypto Pay; Platega и ЮKassa используют свои
сроки счета, которые этот адаптер не меняет. Локальный срок заказа и обработку
поздней оплаты приложение задает отдельно, не выводит из общего поля запроса.

Общие операции:

- `create(request, operation_id=...)` выполняет одну попытку создания счета.
- `get(provider_id, binding=..., invoice_operation_id=...)` запрашивает сервер
  провайдера и проверяет нативный идентификатор, номинальную сумму, валюту,
  получателя и ссылку на исходную операцию.
- `invoice_event(...)` повторно запрашивает состояние и возвращает
  `ProviderEvent(kind="invoice-created")`. Само создание счета не дает доступ.
- `payment_event(...)` повторно запрашивает состояние и допускает `paid` только
  после окончательной оплаты. Для Platega эта операция пока недоступна.

`RefundRequest(binding, charge_id, amount, invoice_operation_id)` сохраняет
привязку возврата к конкретному списанию. Сумма положительна, не превышает цену,
имеет ту же валюту и показатель; частичный возврат требует политики заказа.
Проверку совокупного невозвращенного остатка и прав оператора выполняет
`SQLitePaymentLedger` внутри своей транзакции при резервировании и запуске.
Адаптер не заменяет эту проверку и не разрешает повторно отправлять уже
запущенную операцию.

`ProviderInvoice`, `ProviderRefund` и `ProviderNotification` — обычные структуры
данных, не удостоверения подлинности. Вручную созданная структура не становится
доказательством оплаты. Уведомление служит поводом найти серверный заказ и
запросить актуальное состояние. Возвращение браузера на `return_url` не является
платежным событием.

Суммы хранятся как `Money`. Crypto Pay и ЮKassa получают точные десятичные строки;
Platega получает десятичное JSON-число, сформированное без `float`. Ответы с
числовыми суммами разбираются через `Decimal`, без округления при низкой точности
его глобального контекста. Показатели Platega и ЮKassa в этом узком адаптере
ограничены двумя знаками. Crypto Pay отдельно проверяет документированный набор
фиатных валют/криптовалют и режим счета. Сумма фактически полученной криптовалюты
и комиссия не подменяют номинал фиатного заказа.

## HTTP и граница доверия

Приложение реализует `AsyncTransport[ProviderHttpRequest, ProviderHttpResponse]`.
Его `send(request)` обязано проверять сертификат HTTPS, запрещать перенаправления
и автоматические повторы, соблюдать `timeout_seconds` и прерывать чтение потока
при превышении `max_response_bytes`. Ограничение применяется до накопления всего
ответа. Адаптер дополнительно ограничивает ожидание и размер уже полученных
байтов, отвергает перенаправления, повторяющиеся JSON-ключи, нечисловые значения
и слишком глубокие структуры. Подставленный транспорт — доверенная серверная
реализация; тестовая реализация не доказывает сетевую аутентификацию.

По умолчанию ожидание — 15 секунд, ответ — 256 КиБ. Настраиваемые пределы:
1–60 секунд и 1 КиБ–1 МиБ. Адрес API фиксируется внутри адаптера; произвольный
адрес сервера и адрес для Platega «sandbox» не принимаются. Заголовки, тела и
секреты скрыты из `repr`, в безопасный отчет об ошибке не копируется текст
исключения провайдера. Полные тела могут содержать персональные данные:
приложение не должно отправлять их в журнал диагностики.

Сверка — запрос фактического состояния провайдера перед выдачей или повтором.
Неизвестный результат означает, что внешний эффект мог произойти, хотя надежного
ответа нет. Таймаут, разрыв связи, неоднозначный HTTP-ответ, неверное тело успешной
записи и отмена ожидания не доказывают отсутствие эффекта. `ProviderWriteUnknown`
дает `unknown/reconcile` через `safe_error_report(..., operation="write")`.
Адаптер сам ничего не повторяет. `CancelledError` распространяется наружу:
приложение обязано сохранить запущенное намерение как требующее сверки, а не как
удаленно отмененное.

Ошибка чтения, пустой поиск и HTTP 404 дают `ProviderReadFailure`: отсутствие
найденного объекта не исключает позднее создание или оплату. HTTP 429 чтения
дает `ProviderRateLimited(retry_after)` с целым пределом 0…86400 секунд либо
`None`. Повторы чтения, общий срок, число попыток и ограничения частоты задает
приложение. HTTP 429 записи консервативно остается неизвестным результатом.

## Crypto Pay

`CryptoPayAdapter(..., merchant_id=..., token=..., environment="testnet",
currency_type="fiat")` принимает токен платежного приложения, не токен бота.
Среды фиксированы: `https://testnet-pay.crypt.bot/api/` и
`https://pay.crypt.bot/api/`. Соответствие токена серверному `merchant_id`
настраивает владелец приложения: адаптер не выдумывает отсутствующие в описании
`getMe` поля идентификации магазина.

Счет передает `payload` с полной привязкой, строковый `amount`, выбранные
`currency_type` и `fiat`/`asset`. Поле `return_url` общего запроса здесь не
передается как вымышленный параметр Crypto Pay. Пользователь получает
`bot_invoice_url` из ответа провайдера. Результат `getInvoices` допускает
документированный список и распространенную оболочку `items`; соответствие
реальному ответу конкретного приложения еще требует проверки.

`verify_event(body, headers)` вычисляет HMAC-SHA-256 от **исходных байтов** тела;
ключ — SHA-256 токена, заголовок — `crypto-pay-api-signature`. Сравнение выполняется
за постоянное время. Пересериализованное тело проверять нельзя. Проверяются вид
`invoice_paid` и формат `request_date`; автоматического отбрасывания старых
подписанных повторов нет, поскольку провайдер повторяет доставку в течение
нескольких дней. Приложение хранит принятые уведомления надежно и ограничивает
нагрузку. Для выдачи `payment_event()` все равно делает аутентифицированный GET.
Неуникальный `update_id` не используется как финансовый ключ: событие оплаты
опирается на нативный `invoice_id`, статус `paid` и время `paid_at`.

`refund()` возвращает `UnsupportedCapability`: в проверенном перечне методов
нет нативного возврата счета. Метод `transfer` не является возвратом и не
подставляется вместо него. Подписки также не реализованы.
[Официальный Crypto Pay API](https://help.send.tg/en/articles/10279948-crypto-pay-api)

Если ответ `createInvoice` потерян **до сохранения нативного `invoice_id`**,
адаптер не может найти счет по `operation_id`: такого метода поиска он не
предоставляет, а `payload` не превращается в выдуманный поисковый endpoint.
Нужно оставить намерение неизвестным и выполнять операторскую/провайдерскую
сверку с подтвержденной привязкой счета. После надежного получения нативного ID
доступен обычный GET и сравнение полной привязки. Получение ID не гарантировано;
до закрытия неопределенности второй счет не создается. Знание ID из отдельной
базы тестового провайдера в тесте падения процесса моделирует доверенную операторскую
находку, а не существующий метод Crypto Pay.

## Platega

`PlategaAdapter(..., merchant_id=..., native_merchant_id=..., secret=...,
payment_method=...)` использует только `https://app.platega.io/`. Метод оплаты
выбирается по настройкам магазина. `create(..., customer_email=...)` требует
серверные данные покупателя: `metadata.user_email` и привязанный `userId`.
Выдумывать почту или копировать пример магазина нельзя. Создание отправляет
актуальные `paymentMethod`, `paymentDetails`, `payload`, `return`, `failedUrl`;
идентификатор транзакции назначает провайдер. У создания нет выдуманного
заголовка идемпотентности.
[Создание платежа](https://docs.platega.io/создание-платежной-ссылки-с-заданным-методом-29203843e0)

Уведомления проверяются по `X-MerchantId` и `X-Secret`. Это схема платежных
уведомлений, не подпись из другого протокола выплат. Текущая опубликованная схема
использует `camelCase`; поле получателя в ответе GET написано **`mechantId`**.
Адаптер проверяет именно его и не создает несуществующее поле нормализацией.
`CONFIRMED` может прийти повторно после спора и не означает второе списание.
[Статус платежа](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0),
[Уведомления](https://docs.platega.io/колбэки-общая-информация-2499110m0),
[CONFIRMED](https://docs.platega.io/confirmed-29209725e0)

Опубликованные GET и уведомление `CONFIRMED` не содержат нативного времени
оплаты. `ProviderEvent.paid_at` текущего ledger означает время платежа провайдера.
Поэтому `payment_event()` пока возвращает `UnsupportedCapability`: время
наблюдения, получения HTTP-ответа и начало периода подписки не подставляются
вместо времени платежа. `get()` предоставляет проверенный статус для дальнейшего
контракта магазина. Это реальная граница интеграции, а не завершенная выдача
доступа Platega через общий ledger.

`refund_support(request)` выполняет привязанный GET и проверку
`cancel-supported`; частичная сумма идет в query. `refund(...,
approve_cost=...)` требует точное `True` от серверной проверки стоимости:
`total_deduct_usdt` и `penalty_usdt` не разрешают незаметно списывать комиссию.
Это отдельная проверка стоимости вне SQLite; она не заменяет права оператора
в транзакции ledger. Полный возврат использует `/cancel` без тела и суммы.
Частичный — `/cancel-partial`, числовой `amount` и документированный
`Idempotency-Key`. `accepted`, `accepted=false` для уже выполняемой операции и
`manualControlRequired` остаются промежуточными состояниями.
[Проверка возврата](https://docs.platega.io/проверка-возможности-отмены-транзакции-38219023e0),
[Полный возврат](https://docs.platega.io/отмена-транзакции-38225949e0),
[Частичный возврат](https://docs.platega.io/частичная-отмена-транзакции-45635137e0)

Приложение надежно сохраняет полученный `refundOperationId` вместе со своей
операцией. `refund_event(request, provider_refund_id, body, headers, ...)`
требует совпадения с этим идентификатором, аутентифицированное уведомление с
`refundStatus="Succeeded"`, точные исходную и возвратную суммы, валюту и
привязку, затем актуальный GET с `CHARGEBACKED`/`PARTIALLY_REFUNDED`.
`CHARGEBACKED` без индивидуального `refundId` нельзя автоматически приписывать
локальному частичному возврату. Если нативный идентификатор не получен, требуется
подтвержденная сверка магазина; новый возврат автоматически не отправляется.
[Поля возврата](https://docs.platega.io/поля-колбэка-по-возврату-18505579d0),
[CHARGEBACKED](https://docs.platega.io/chargebacked-40030962e0),
[PARTIALLY_REFUNDED](https://docs.platega.io/partially-refunded-45635294e0)

## ЮKassa

`YooKassaAdapter(..., merchant_id=..., shop_id=..., secret_key=..., test=...)`
использует HTTP Basic и фиксированный `https://api.yookassa.ru/v3/`; тестовый
и рабочий магазины имеют один адрес. Проверяются `recipient.account_id` и
точный `test` из ответа. В `metadata` отправляются полная привязка и исходный
идентификатор операции. `create()` по умолчанию сохраняет одностадийный платеж с
`capture=true`. Двухстадийный сценарий выбирается явно:
`create(..., options=YooKassaCreateOptions(capture=False))`.
`waiting_for_capture` даже при `paid=true` доступа не дает.
Событие оплаты требует `succeeded`, `paid=true` и нативное `captured_at`.
[Протокол и идемпотентность](https://yookassa.ru/developers/using-api/interaction-format),
[Официальная схема объектов](https://yookassa.ru/developers/using-api/openapi-specification)

У записей используется **`Idempotence-Key`** до 64 символов: устойчивый хеш
серверной привязки и операции. Провайдер сохраняет идемпотентность 24 часа;
истечение этого окна не разрешает повтор неизвестной операции. `refund()`
создает настоящий полный/частичный возврат, `get_refund()` проверяет нативный
возврат и связанный платеж, `refund_event()` допускает только окончательный
`succeeded` с точной суммой. Возврат `pending` не освобождает резерв. Приложение
должно сохранять соответствие нативного идентификатора возврата своей операции.

`capture(binding, provider_id, invoice_operation_id=..., operation_id=...)`
списывает только **полную неизменяемую сумму** заказа. Сначала выполняется
аутентифицированный GET: совпадают получатель, среда, сумма/валюта, нативный ID,
полная привязка и исходная операция; обязательны `waiting_for_capture` и
`paid=true`. Затем выполняется один POST `/payments/{id}/capture` с точной
строкой `Money` в `amount`. Перед сетью приложение сохраняет результат
`capture_key(binding, provider_id, invoice_operation_id=..., operation_id=...)`:
64-символьный ключ имеет отдельное пространство `capture` и включает полную
привязку, исходную операцию создания, нативный платеж и операцию списания.
Он отличается от ключей создания/возврата и не меняется при восстановлении.

После POST адаптер делает независимый GET. Только текущие `succeeded`,
`paid=true`, точная привязка и нативное `captured_at` позволяют вернуть успешный
снимок. Успешный POST без этого GET, промежуточный статус, потеря ответа,
непонятное тело и отмененный между проверками платеж оставляют
`ProviderWriteUnknown`; нового POST адаптер не делает. Отмена асинхронного
ожидания не означает удаленную отмену платежа. Выдача доступа по-прежнему идет
через `payment_event()` и транзакцию ledger, а не по сконструированному снимку.

ЮKassa документирует частичное списание для определенных способов оплаты и
автоматический возврат остатка. Этот компонент поддерживает полное списание:
он не определяет возможности конкретного способа и не меняет полную сумму
неизменяемой привязки ledger на частично списанную. Параметра частичной суммы
у `capture()` нет. Точный срок холдирования задает нативное `expires_at`,
не общий срок из `InvoiceRequest`. Между GET и POST платеж может истечь или
быть отменен; это не атомарная блокировка провайдера. Отдельного API отмены
авторизации этот компонент пока не предоставляет.
[Официальный процесс платежа, подтверждение и отмена](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process)

HMAC для уведомлений не выдумывается. `verify_event(body, headers)` всегда
возвращает `None`: одни заголовки недостаточны. Для входящего запроса есть
`verify_notification(body, peer_ip=...)` и `YooKassaPeerPolicy` с опубликованными
сетями провайдера. `peer_ip` берется из сокета либо из контекста, который сервер
получил через фиксированную доверенную конфигурацию прокси. Произвольные
`Forwarded`/`X-Forwarded-For` клиента не подходят. Перед финансовым переходом
в любом случае выполняется серверный GET; сетевой допуск уведомления не заменяет
сравнение текущего платежа с заказом.
[Уведомления и адреса отправителей](https://yookassa.ru/developers/using-api/webhooks)

`OAuth`, частичное списание, автосписания, подписки, раздельные выплаты,
налоговые чеки и настройка фискализации не реализованы этим узким адаптером.
Перед внедрением магазин
должен подтвердить, подходит ли поддержанный запрос его договору и схеме чеков;
если обязательны дополнительные параметры, нужен отдельный проверенный контракт,
а не выдуманные налоговые поля.

## Сохранение намерения и локальные доказательства

До HTTP-записи приложение сохраняет намерение; поддержанные операции ledger
запускаются через `SQLitePaymentLedger.start_operation()`. Приложение также надежно хранит точное
провайдерское намерение: описание, параметры магазина, ссылки, покупательские
данные, ключ и соответствие нативных идентификаторов. Общий ledger не хранит
все тело HTTP-запроса и не является таблицей ожидающих уведомлений провайдера.
Новый ключ не используется для обхода неизвестного исхода старого запроса.
Ожидающие/неизвестные возвраты удерживают бюджет, истечение владения работником
не разрешает второй вызов. Отмена локального ожидания не отменяет внешний эффект.

В ledger пока нет вида операции `capture`; выдавать его за `invoice` или
`refund` нельзя. Конкретная композиция без новой инфраструктуры показана в
`examples/python/offline_providers.py`: `SQLiteOutbox` и ledger используют
один файл SQLite. Приложение сохраняет через `enqueue()` в своей писательской
транзакции полную привязку, нативные ID, обе операции, параметры магазина,
ссылку на секрет, точный метод/путь/тело и устойчивый ключ. Секрет в тело
журнала не копируется. Повтор ключа с измененным намерением конфликтует.
После фиксации транзакции работник получает `claim()` и только затем вызывает адаптер.
Пример сохраняет намерения создания, списания и возврата, а нативные ID —
в результатах журнала; `max_attempts=1` исключает повторную отправку после доказанной
неудачи без нового отдельно разрешенного намерения.

При таймауте/отмене работник вызывает `mark_unknown()` либо истекшее владение
восстанавливается через `recover_expired()`. Для списания с известным платежом
проверенный GET позволяет сверить исход: `reconcile(..., outcome="sent",
expected_revision=..., evidence_ref=...)` сохраняет доказательство, а
идемпотентное событие `paid` отдельно обновляет ledger. Сбой между этими двумя
локальными переходами исправляется повторным GET и применением события;
две транзакции не объявляются одной атомарной операцией. Неокончательный
GET оставляет запись неизвестной. Пустой поиск не разрешает `outcome="absent"`.
Серверное право на платежную операцию проверяет приложение до постановки и
перед отправкой; сведения клиента не создают это право. Входящие уведомления
также нуждаются в собственном надежном журнале до HTTP-подтверждения.

Запросы провайдера выполняются **вне** SQLite-транзакции. Доверенная серверная
оркестрация сначала ожидает `payment_event()`/`refund_event()`, затем передает
именно проверенное событие через ограниченный синхронный `verify` в ledger.
Сетевой запрос нельзя делать внутри писательской транзакции или заменять
проверку функцией, принимающей произвольный DTO от клиента. См. также
`docs/payment-ledger.md` и работающий локальный пример
`examples/python/offline_providers.py`.

Проверки `test_provider_*.py` используют заданные контрактом ответы и подставной
транспорт без сети. Три сценария **ЮKassa fixture** с `spawn`, `os._exit`, отдельной
SQLite-базой тестового провайдера и повторным открытием ledger доказывают локальную границу:
эффект переживает потерю ответа, операция становится неизвестной, повторной
записи нет, сверка применяет результат один раз. Они не доказывают работу
кабинетов, TLS конкретного транспорта, доступность методов магазина, настоящую
подпись уведомления, налоговый сценарий или успешный платеж в тестовой сети.

Проверено 2026-11-05: официальные страницы Platega и ЮKassa, в том числе схема
ЮKassa по официальной ссылке. Crypto Pay: использован индексированный текст
официальной страницы API 1.5.2; прямое автоматическое чтение страницы отвечает
403. Это ограничение источника и отсутствие проверки кабинета сохраняются в
приемке. Это исходная сверка 5 ноября; она не подтверждает кабинеты, настоящие
платежи или будущие изменения API. Публикация и production-приемка не выполнялись.

### Дополнительные durable-сценарии 6 ноября

`test_provider_cryptopay_durable.py` и `test_provider_platega_durable.py` выполняют
восемь отдельных сценариев на установленном wheel 0.28.0. Внешняя сеть запрещена;
приложение и подставной провайдер используют разные файловые SQLite-базы.
Настоящие библиотечные adapters проверяют уведомление, затем независимо читают
статус через подставной transport. Журнал уведомления записывается до дальнейшей
обработки. Повтор и открытие БД заново не удваивают эффект, в том числе после
введенной ошибки между commit ledger и завершением receipt. Это исключение
тестового приложения, не доказательство аварийного выключения процесса.

Crypto Pay отдельно проверяет два разных invoice с одинаковым `update_id`.
Потерянный ответ create сохраняет исходную неизвестную операцию и запрещает
второй create с прежним или новым operation ID. Обнаружение native ID в таком
fixture явно выполняет его оператор; отсутствующий поиск по operation ID не
выдумывается. Дальнейшая сверка делает независимый GET.

Platega проверяет неправильную сумму, повтор, новый запуск и потерянный ответ
через подтверждение создания invoice. Отсутствующее нативное время оплаты
по-прежнему закрывает `payment_event`: paid charge и доступ не создаются,
возврат без подтвержденного charge запрещен. Этот локальный результат не
обещает полный оплачиваемый сценарий Platega.

6 ноября повторно прочитаны официальные страницы Platega о создании,
callbacks, GET и возвратах. Прямое чтение Crypto Pay снова вернуло 403;
доступен индексированный текст официальной API 1.5.2, crawl которого старше
даты проверки. Проверены перечисленные фрагменты HMAC, IDs и методов; свежесть
всего API не подтверждена. Sandbox-проверки обоих кабинетов отсутствуют и
сохраняются отдельным ограничением. Локальный результат, актуальность источника
и живая приемка не объединяются в один статус.
