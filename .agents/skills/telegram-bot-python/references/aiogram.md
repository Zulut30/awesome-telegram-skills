# Ветка aiogram

Термины: **ACK** — ответ на нажатие кнопки через `answerCallbackQuery`: клиент убирает индикатор ожидания; это не сообщение об успехе операции.

Применяется к aiogram 3.x; для существующего проекта 2.x сначала уточните его API, не выполняйте миграцию как побочный эффект.

- В 3.x используйте `Router` для маршрутизации, `Dispatcher` для сборки и соответствующие версии фильтров. Не переноситесь к `executor` и декораторам из старых примеров.
- Проверяйте порядок подключения routers и middleware: общий обработчик способен перехватить событие раньше специализированного.
- Передавайте прикладные зависимости через поддерживаемый контекст или явные параметры; не создавайте соединение с БД на каждое сообщение без управления его временем жизни.
- Для FSM сверяйте стратегию ключей, storage и event isolation с фактической конкурентной обработкой updates.
- Для polling и webhook используйте lifecycle установленной версии, включая закрытие bot session. Изменение регистрации webhook относится к конфигурации конкретного бота.
- Если событие нельзя потерять, сверьте polling ACK с фактическим dispatcher: режим `handle_as_tasks=True` допускает следующий getUpdates до завершения handler. `handle_as_tasks=False` упорядочивает обработку, но не гарантирует повтор после исключения, которое SDK уже перехватил. Нужен согласованный надежный прием/восстановление, а не только настройка concurrency.

Источники: [aiogram](https://docs.aiogram.dev/en/latest/), [FSM](https://docs.aiogram.dev/en/latest/dispatcher/finite_state_machine/index.html). Документацию сопоставляйте с версией в lockfile; ссылка `latest` сама по себе не доказывает совместимость проекта.

Механика ACK: [getUpdates](https://core.telegram.org/bots/api#getupdates), [aiogram dispatcher source](https://docs.aiogram.dev/en/latest/_modules/aiogram/dispatcher/dispatcher.html); сверено 3 октября 2026 года.
