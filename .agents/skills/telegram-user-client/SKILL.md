# Пользовательский клиент Telegram

## Когда использовать

Пользователь явно просит работать от имени своего аккаунта: читать историю выбранных чатов, сохранять ее, слушать новые сообщения в них.

## Когда не использовать

Обычный бот через Bot API — telegram-bot-python. Ограниченный доступ к подключенным чатам Business-аккаунта сначала оцените через официальный Business-бот (telegram-business-bots). Массовые рассылки, вступление в группы и сбор контактов от имени пользователя — не задача этого скилла.

## Алгоритм

1. **Задача и границы.** Определите аккаунт, список разрешенных чатов, глубину истории и направление работы (только чтение или еще и действия). Для Python отправной вариант — Telethon.
2. **Авторизация.** Нужны `api_id`, `api_hash` и пользовательская сессия. Токен бота в MTProto дает только идентичность бота, без доступа к чатам пользователя. Вход выполняет владелец аккаунта отдельно; без порученного входа подготовьте код и проверьте его на подставном клиенте.
3. **Сессия как секрет.** Файл сессии или `StringSession` содержит полномочия аккаунта: храните вне исходников, с ограниченным доступом, не выводите в логи и ответы. После отзыва сессии скрипт завершается понятной ошибкой, а не входит заново в цикле.
4. **История.** Читайте только разрешенные чаты через `iter_messages(entity, min_id=checkpoint, reverse=True)`; checkpoint по паре «чат + ID сообщения» фиксируйте вместе с сохраненными сообщениями. `FloodWaitError` обрабатывайте ожиданием `error.seconds` и продолжением от checkpoint, а не пропуском чата.
5. **История и новые сообщения.** Клиент при этом только читает: сообщения не отмечаются прочитанными, ничего не отправляется. Обработчики новых сообщений регистрируйте до чтения истории; сохранение — вставка или обновление по ключу `(peer_id, id)`, поэтому дубли на стыке не появляются. Checkpoint двигает только чтение истории. Telethon переподключается сам (`auto_reconnect=True`), но updates за время обрыва могут не прийти: включите `catch_up=True`, а при старте и периодически вызывайте чтение истории от checkpoint. Правки (`events.MessageEdited`) обновляют строку, удаления (`events.MessageDeleted`) помечают ее; уведомление об удалении приходит не всегда, а правки за время простоя чтение от checkpoint не вернет.
6. **Только чтение.** Чтение не отмечает сообщения прочитанными (`send_read_acknowledge` не вызывается) и ничего не отправляет — прямо скажите это в описании решения. Отправку, вступление в группы, отметку прочитанного и выгрузку контактов добавляйте только по конкретному сценарию. Секретные чаты в облачной истории недоступны.
7. **Ограничения сервера.** Ограничивайте параллельность запросов; не обходите лимиты сменой аккаунтов или повторными входами.

Готовый скрипт выгрузки с checkpoint и разбор стыка истории с новыми сообщениями — в [references/telethon.md](references/telethon.md).

## Пример

```python
from telethon import TelegramClient, events

client = TelegramClient(session, api_id, api_hash, catch_up=True)  # session — StringSession из секретов


@client.on(events.NewMessage(chats=ALLOWED))
@client.on(events.MessageEdited(chats=ALLOWED))
async def on_message(event) -> None:
    save(event.chat_id, event.message)  # вставка или обновление по (peer_id, id)
    db.commit()


@client.on(events.MessageDeleted())
async def on_deleted(event) -> None:
    # chat_id есть только в каналах и супергруппах; в личных чатах и малых группах ID уникален в аккаунте
    mark_deleted(event.chat_id, event.deleted_ids)  # deleted = 1, строка не удаляется
    db.commit()


async def run() -> None:
    await client.connect()  # обработчики уже зарегистрированы: новые сообщения не потеряются
    for chat in ALLOWED:
        await read_history(client, chat)  # от checkpoint; FloodWaitError — пауза и продолжение
    await client.run_until_disconnected()  # только чтение: прочитанным не отмечает, сообщений не отправляет
```

Скрипт только читает: сообщения в чатах остаются непрочитанными, клиент ничего не отправляет и никуда не вступает.

## Типичные ошибки

- Вход токеном бота ради истории личных чатов пользователя.
- Чтение всех диалогов вместо списка разрешенных чатов.
- `FloodWaitError` пойман вне цикла: чат пропускается, а не дочитывается.
- Checkpoint двигается из обработчика новых сообщений: при сбое остается дыра.
- Ключ сообщения — только `id`: в разных каналах ID повторяются.
- Строка сессии в коде, логах или репозитории.

## Проверка

На подставном клиенте проверьте: только разрешенные чаты, повтор события, `FloodWaitError` посреди выгрузки, checkpoint после рестарта и переподключения, недоступный чат, правку и удаление. Тестовые сообщения пишите вручную в обычном приложении Telegram, а не из проверяемого скрипта; после прогона сообщения в чате должны остаться непрочитанными. С авторизованной тестовой сессией проверьте один выбранный чат, не публикуя его содержимое. Результаты без сети и с живым аккаунтом отмечайте отдельно.

В описании решения перечислите: ключ, по которому отсеиваются дубли; где двигается checkpoint; что происходит после переподключения; как учтены правки и удаления; и что клиент только читает — не отмечает сообщения прочитанными и ничего не отправляет.
