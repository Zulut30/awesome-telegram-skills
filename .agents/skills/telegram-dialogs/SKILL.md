# Диалоги и состояние

Постройте небольшую таблицу переходов: текущее состояние → допустимый ввод → проверка → действие → следующее состояние. Учтите старт, отмену, возврат, таймаут и повторный вход. Для обычного меню не создавайте FSM без необходимости.

## Ключи и долговечность

Выберите ключ по смыслу сценария: отдельный пользователь, пользователь в чате, пользователь в теме либо общий процесс группы. Разделяйте временные ответы формы и долговечные бизнес-объекты. Укажите, должен ли диалог переживать рестарт и работать на нескольких экземплярах.

При конкурирующих updates сериализуйте переходы одного диалога либо используйте атомарную версию состояния. Переход, создающий заказ или запись, должен иметь защиту от повторного выполнения независимо от UI.

Для aiogram используйте FSM установленной версии. Для python-telegram-bot проверьте ConversationHandler, persistence и настройки concurrency. В другом framework используйте существующий механизм; не мигрируйте весь бот ради диалога.

## Кнопки и входные данные

Старые сообщения остаются доступными: callback должен проверять текущую версию процесса, владельца и допустимость действия. Просроченная кнопка должна давать понятный ответ, а не изменять уже завершенный объект.

Подтверждайте callback через `answerCallbackQuery` установленного SDK, включая старую кнопку, отказ и повтор. Для длительной операции ответь до ее выполнения, не объявляя еще не сохраненный переход успешным. ACK (ответ `answerCallbackQuery`) убирает индикатор ожидания клиента; `sendMessage` или редактирование сообщения его не заменяют.

Не доверяйте callback payload и тексту сообщения как полномочию. Валидируйте каждый шаг на сервере. Команды отмены и помощи должны быть доступны там, где пользователь может застрять. На неожиданный тип сообщения сообщите ожидаемое действие без потери состояния.

Если операции длительные, покажите пользователю принятый запрос и предусмотренный продуктом способ узнать результат. Ограничивайте сохраненные данные сроком, соответствующим сценарию.

## Проверка

Проверьте успешный путь, отмену на промежуточном шаге, неверный ввод, два быстрых нажатия, старую кнопку и восстановление после рестарта, если оно обещано. Отдельно проверьте, что два пользователя не разделяют ответы формы.

С библиотекой awesome-telegram-patterns, если она уже есть в проекте: [поля диалогов](references/dialog-fields.md) и [восстановление формы после рестарта](references/dialog-restart.md). Без нее те же проверки делайте средствами текущего SDK.
