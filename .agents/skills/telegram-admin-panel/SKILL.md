# Админка Telegram-сервиса

## Когда использовать

Нужен интерфейс для операторов сервиса: найти заказ или пользователя, поправить данные, выполнить разрешенное действие, посмотреть журнал. Подходит для Mini App, веб-панели и админских команд бота.

## Когда не использовать

Экраны для обычных пользователей Mini App — telegram-mini-app-ui. Проверка initData и выдача сессии — telegram-mini-app-auth. Универсальная CRM вместо конкретной операционной задачи не нужна.

## Алгоритм

Определите операторов, их действия и текущий интерфейс: Mini App, веб-панель или команды бота. Сохраняйте выбранный формат и стек. Не превращайте небольшую операционную задачу в универсальную CRM.

### Действия и права

Для решений по roles, таблицам и операциям прочитайте [references/operations.md](references/operations.md). Начните с одного сквозного пути, например найти заказ → посмотреть состояние → выполнить разрешенную корректировку → увидеть запись журнала.

Backend проверяет проверенную личность, роль/capability и scope объекта при каждом чтении и изменении. Telegram ID из frontend, username, членство в группе или скрытая кнопка сами не дают административного доступа. Отзыв роли учитывается до выполнения существенного действия.

Для опасного/финансового действия покажите конкретный объект, эффект и основание подтверждения по риску. UI preview и confirmation не заменяют authorization, concurrency и идемпотентность backend. Возврат платежа выполняется адаптером провайдера; смена статуса строки не является возвратом.

### Интерфейс

Поиск, фильтры, pagination и сортировка должны сохранять scope и иметь понятные empty/error/loading. На широком экране полезен список с деталями, на узком — последовательный путь к тому же объекту. Сохраняйте фильтры и позицию возврата без второго источника серверного состояния.

Bulk action показывает область выбора: текущая страница или весь отфильтрованный набор. Состав фиксируется snapshot/контрактом, права перепроверяются при выполнении. Частичный результат отображается по объектам; retry касается нужных операций, не всего успешного набора.

Журнал связывает инициатора, действие, объект, время и исход с correlation/operation ID. Секреты и полные личные данные в него не копируются. Возможность читать/export журнал также имеет право и scope.

## Проверка

Проверьте прямой запрос без роли, чужой tenant/object, отзыв права между просмотром и submit, устаревшую revision и повтор операции. Для массового действия воспроизведите частичный отказ и корректный повтор.

При реализации выполните frontend typecheck/build и backend сценарий с реальным выбранным storage, если он изменялся. Fake provider подтверждает маршрутизацию операции, но не настоящий возврат. Укажите среду и результат, отдельно от плана.

## Типичные ошибки

- Доступ к админке дается по Telegram ID из frontend, username, членству в группе или скрытой кнопке.
- Права проверяются только при входе, а отзыв роли не учитывается до выполнения действия.
- Подтверждение в интерфейсе считается защитой от гонки и повтора; backend не проверяет версию объекта.
- Смена статуса строки выдается за возврат платежа без вызова адаптера провайдера.
- Массовое действие не показывает, затронута страница или весь отфильтрованный набор, а повтор запускает все заново.
