# Проверка initData

Перед изменением алгоритма сверь [официальную схему Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app). Для существующего aiogram есть [WebApp utils](https://docs.aiogram.dev/en/latest/utils/web_app.html).

## HMAC на сервере владельца бота

Разбери URL-encoded строку в пары с однократным декодированием. Сохрани полученные строковые значения без повторной JSON-сериализации. Отклоняй неоднозначные дубли, отсутствующие обязательные поля и неверный формат подписи.

Исключи `hash`, отсортируй остальные поля по имени и соедини `key=value` через LF (`\n`). Если присутствует `signature`, в HMAC-пути она остается подписанным полем. Не переноси исключение `signature` из Ed25519-пути в HMAC.

```text
secret_key = HMAC_SHA256(key = UTF8("WebAppData"), message = UTF8(bot_token))
expected = HMAC_SHA256(key = secret_key, message = UTF8(data_check_string))
```

Первый результат используй как байты, а не hex-строку. Сравни ожидаемые байты с декодированным `hash` в constant time. Проверь `auth_date` с серверным временем и явно заданной политикой свежести.

## Проверка третьей стороной

Если проверяющей стороне нельзя раскрывать токен бота, изучи отдельную Ed25519-схему Telegram с `bot_id` и ключом нужной среды. У нее другой data-check-string и исключаются `hash` и `signature`. Пользуйся проверенной криптографической библиотекой; не передавай bot token сторонней службе ради проверки.

Это описание входных инвариантов, а не готовая криптографическая реализация. При offline-разработке пометь совместимость с текущими данными Telegram как непроверенную.
