# Другой платежный провайдер

## Когда использовать

Нужно подключить Stripe, Robokassa или другого провайдера, для которого нет отдельного скилла, или добавить еще одну платежку к уже работающим.

## Когда не использовать

Оплата цифровых товаров звездами и выбор маршрута оплаты — telegram-payments. ЮKassa — telegram-yookassa, Crypto Pay — telegram-cryptopay, Platega — telegram-platega.

## Алгоритм

1. **Маршрут и документация.** Убедитесь, что внешняя оплата допустима для этого товара в Telegram. Найдите первичную документацию провайдера: создание платежа, проверка уведомлений (webhooks), запрос статуса, отмена и возврат, тестовая среда. В ответе приведите ссылки на разделы официальной документации, на которых основано решение, и отдельный список «Не подтверждено» — то, чего в документации нет или что вы не проверили; не заполняйте это предположениями. Детали Stripe и Robokassa, включая соответствие контракту ниже и коды статусов, — в [references/providers.md](references/providers.md); не придумывайте названия статусов и полей.
2. **Контракт адаптера.** Создать платеж, запросить статус, проверить и разобрать уведомление, вернуть деньги, отменить платеж. Для каждого метода найдите операцию провайдера; возврат и отмена реализуются, если провайдер их поддерживает (у Robokassa возврат — API возвратов, отмена — только для двухстадийной оплаты), иначе метод явно сообщает «не поддерживается». Отметьте возможности: собственная идемпотентность (повтор запроса с тем же ключом не создает второй платеж), двухстадийное списание, рекуррентные платежи, валюты, возвраты, тестовая среда. Отсутствующая функция явно сообщает об этом, а не возвращает поддельный успех.
3. **Модель данных.** Заказ хранит провайдера, магазин, среду (тест или рабочая), ID платежа у провайдера, сумму, валюту, статус и версию. Отдельно — попытки создания с ключом повтора и обработанные уведомления с уникальным ключом «провайдер + ID события или транзакции». Оплата, выдача, возврат и оспаривание платежа — разные состояния.
4. **Создание платежа.** Сохраните попытку до запроса. Ключ повтора или номер счета выбирайте по API провайдера (у Stripe — `Idempotency-Key`, у Robokassa — уникальный `InvId`). Если результат неизвестен (запрос мог выполниться, но ответа нет: таймаут, обрыв связи), сначала сверка (запрос фактического состояния у провайдера) по сохраненной попытке, и только потом повтор.
5. **Уведомление.** Проверьте подлинность способом провайдера: у Stripe — подпись `Stripe-Signature` по сырому телу, у Robokassa — `SignatureValue` с паролем #2 и параметрами `Shp_*`. Затем сумму, валюту, связь с локальным заказом и допустимость перехода. Дубль по ключу «провайдер + ID» ничего не меняет; событие, пришедшее не по порядку, не откатывает подтвержденный статус.
6. **Ответ и выдача.** Успехом провайдеру (2xx, у Robokassa — текст `OK{InvId}`) отвечайте только после надежного сохранения уведомления. Дубль получает такой же успешный ответ: отказ на дубль заставит провайдера повторять уведомление снова. Выдачу выполняйте один раз: в той же транзакции или через outbox (события, сохраненные в той же транзакции, что и изменение данных; отдельный обработчик выполняет их позже).
7. **Возврат пользователя.** Страница возврата (return URL) и скриншот оплаты серверный статус не меняют: покажите «проверяем оплату» и спросите статус у backend. Оплату подтверждает только backend — уведомлением провайдера или запросом статуса — после проверки суммы, валюты и того, что платеж принадлежит именно этому локальному заказу (сохраненный ID платежа или номер счета).
8. **Еще одна платежка.** Существующие заказы, адаптеры и обработчики уведомлений не меняются. Новый адаптер получает свой маршрут уведомлений и свои секреты; выбор провайдера сохраняется в заказе. Не обещайте страны, комиссии и вывод денег по памяти.

## Пример

```python
from dataclasses import dataclass
from decimal import Decimal
from typing import Protocol


@dataclass(frozen=True)
class ProviderEvent:
    provider: str     # "robokassa", "stripe"
    event_id: str     # ID события или транзакции у провайдера
    order_id: str
    amount: Decimal
    currency: str
    status: str       # "succeeded", "canceled", "refunded"


class PaymentProvider(Protocol):
    name: str
    supports: frozenset[str]  # {"refund", "cancel", "two_step", "recurring"} — по документации провайдера
    async def create_payment(self, order_id: str, amount: Decimal, currency: str, idempotency_key: str) -> str: ...
    async def fetch_status(self, order_id: str) -> str: ...
    def parse_notification(self, headers: dict[str, str], body: bytes) -> ProviderEvent: ...  # ValueError при неверной подписи
    async def refund(self, order_id: str, amount: Decimal, idempotency_key: str) -> str: ...
    async def cancel(self, order_id: str) -> str: ...  # нет в supports — исключение «не поддерживается», а не успех


FORWARD = {"pending": {"succeeded", "canceled"}, "succeeded": {"refunded"}}


async def apply_event(db, event: ProviderEvent) -> None:
    async with db.transaction():  # ошибка откатывает и запись о событии
        if not await db.insert_once("provider_events", provider=event.provider, event_id=event.event_id):
            return  # дубль уже обработан
        order = await db.lock_order(event.order_id, provider=event.provider)
        if order is None or (event.amount, event.currency) != (order.amount, order.currency):
            raise ValueError("уведомление не совпадает с заказом")
        if event.status in FORWARD.get(order.status, set()):  # старое событие не откатывает статус
            await db.set_status(order, event.status)
            if event.status == "succeeded":
                await db.add_outbox("grant_access", order_id=order.id)
```

```python
async def notification_endpoint(provider: PaymentProvider, db, headers: dict[str, str], body: bytes) -> int:
    try:
        await apply_event(db, provider.parse_notification(headers, body))  # дубль завершается без изменений
    except ValueError:
        return 400  # неверная подпись или чужой заказ: ничего не изменено
    return 200  # после фиксации транзакции, и для дубля тоже; у Robokassa тело ответа — OK{InvId}
```

## Проверка

В тестовой среде провайдера (у Robokassa — `IsTest=1` и тестовые пароли) проверьте: неверная подпись дает отказ без изменения заказа; повтор уведомления дает один эффект; события не по порядку; потерянное уведомление восстанавливается сверкой статуса; таймаут создания не создает второй платеж. Если документация неполная, реализуйте известные части и перечислите неподтвержденные пункты в ответе.

## Типичные ошибки

- Поля подписи и статусы одной платежки перенесены в другую: у Robokassa в подпись уведомления добавлен `MerchantLogin`, взят пароль #1 вместо #2 или `Shp_*` не отсортированы.
- Заказ помечен оплаченным по return URL или скриншоту.
- Дубли отсеиваются по тексту уведомления или только по ID заказа, а не по ключу «провайдер + ID события или транзакции».
- Ответ 200 до сохранения, выдача до фиксации транзакции или выдача при каждом повторе уведомления.
- После таймаута создания платеж создается заново без сверки — у пользователя два счета.
- Событие не по порядку возвращает оплаченный заказ в «ожидает оплаты».
- Пароли, `whsec_...` и ключи API в коде или логах; тестовые и рабочие ключи перепутаны.
