# Другой платежный провайдер

Установи поставщика, продукт и разрешенный платежный маршрут. Выбери первичную документацию: официальные API, authentication, webhooks и sandbox. Для примеров провайдеров прочитай [references/providers.md](references/providers.md). Не переноси поля подписи и статусы одной платежки в другую.

Перед кодом составь малый контракт adapter: create checkout, fetch status, verify notification, cancel/refund только при поддержке и потребности. Пометь capabilities: provider idempotency, capture, recurring payments, currencies, refunds и тестовая среда. Отсутствующая функция должна быть явной, а не fake успешным ответом.

Локальная модель заказа не зависит от одного SDK. Храни provider, merchant/environment, transaction ID, attempts и fulfillment key. Разделяй состояние оплаты, выдачу, возврат и chargeback. При неизвестном результате создания сначала сверяй attempt; ключ повторения выбирай по официальному API.

Проверяй источник уведомления документированным способом, затем сумму, валюту, локальную связь и допустимость перехода. Возвращай ACK после надежного приема, а side effects делай один раз через транзакцию/outbox. Return URL и screenshot оплаты не меняют серверный статус.

Для «добавить еще одну платежку» сохрани существующие заказы и обработчики прошлых провайдеров. При выборе доступного способа оплаты показывай актуальную capability выбранного merchant; не обещай страны, комиссии и вывод денег по памяти.

Проверь новый adapter в sandbox, недействительное уведомление, повтор, out-of-order события и восстановление потерянного callback. Если документация неполная, подготовь известные части и пометь неподтвержденный контракт; не заполняй его предположениями.
