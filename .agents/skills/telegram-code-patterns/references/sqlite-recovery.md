# Резервная копия SQLite и восстановление в новый файл

Термины: **неизвестный результат** — запрос мог выполниться, но ответа нет (таймаут, обрыв связи); повторять вслепую нельзя, сначала сверка; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

Компонент `sqlite-recovery` доступен с 0.28.0 и остается experimental.
`backup_sqlite` создает проверенный снимок одной SQLite-БД. `restore_sqlite_new`
восстанавливает его только по отсутствующему пути. SDK, облако и новый сервис
для этих операций не нужны. Установите предоставленный локальный wheel;
копирование скилла не устанавливает пакет.

## Границы и подготовка

Приложение владеет базой, доступом к файлам, расписанием, хранением копий,
шифрованием при необходимости и планом переключения сервиса. Корневые каталоги
`source_root` и `destination_root` должны существовать и быть защищены от записи
и замены другими пользователями. На Windows заранее проверьте ACL каталога и его
родителей под учетной записью владельца сервиса: библиотека не назначает ACL
и не превращает доступный всем каталог в защищенный. На POSIX защищенная часть
пути должна принадлежать текущему UID и не допускать запись группы/остальных;
у временного примера каталоги имеют режимы 0700.

Оба пути выбирает доверенная конфигурация владельца, а не сообщение Telegram,
имя загружаемого файла или HTTP-параметр пользователя. Относительный путь
разрешается внутри явно указанного корня. `..`, выход из корня, symlink,
Windows reparse point/junction, специальные файлы и совпадение исходника с целью
отклоняются. Корни могут быть разными; неподдерживаемая файловая система
отказывает, а не переключается на небезопасное копирование.

Цель обязана отсутствовать. Операция готовит отдельный файл, открывает исходник
только для чтения через SQLite backup API, проверяет `integrity_check` и
`foreign_key_check` и публикует готовый файл без перезаписи. Снимок включает
зафиксированные данные WAL; простое копирование одного занятого `.sqlite`
не заменяет этот путь. Консистентность нескольких БД и внешних сервисов
этот компонент не устанавливает.

## Публичный API

```python
from pathlib import Path
from telegram_patterns import (
    SQLiteRecoveryError, SQLiteRecoveryResult, backup_sqlite, restore_sqlite_new,
)

# Замените корни своими существующими каталогами с проверенными правами.
data = Path("C:/service-state")
copies = Path("C:/service-backups")
recovery = Path("C:/service-recovery")
try:
    snapshot: SQLiteRecoveryResult = backup_sqlite(
        "live.sqlite", "snapshot-001.sqlite",
        source_root=data, destination_root=copies, deadline_seconds=30,
    )
    restored = restore_sqlite_new(
        "snapshot-001.sqlite", "recovered-001.sqlite",
        source_root=copies, destination_root=recovery, deadline_seconds=30,
    )
except SQLiteRecoveryError as error:
    # code/phase фиксированы; исходные пути и текст SQLite в ошибку не включаются.
    print(error.code, error.phase)
```

| Контракт | Значение |
| --- | --- |
| `source`, `destination` | `str` или `Path`; цель отсутствует, исходник — обычный SQLite-файл |
| `source_root`, `destination_root` | Обязательные существующие корни владельца сервиса |
| `deadline_seconds` | Точное `int`/`float` больше нуля и не больше 300; по умолчанию 30 секунд |
| `SQLiteRecoveryResult` | Неизменяемые `operation`, скрытый из `repr` `destination`, `sha256`, `bytes`, `pages`, `directory_synced`, `cleanup_complete` |
| `SQLiteRecoveryError` | Безопасные `code` и `phase`; путь и исходная ошибка SQLite не выводятся |

Бюджет проверяется при копировании страниц, проверках SQLite и вычислении хеша.
Он не прерывает зависший системный вызов файловой системы, `fsync` или драйвер;
жесткий срок завершения процесса им не обещается.

Файл синхронизируется перед публикацией. На проверенном Windows/NTFS
`directory_synced=False`: атомарная публикация не означает доказанную
долговечность записи каталога при потере питания. На поддерживаемом POSIX
библиотека пытается синхронизировать каталог; успешность отражает поле результата.
`cleanup_complete=False` означает остаток принадлежащего операции временного
каталога: опубликованный файл от этого не становится несуществующим.
Проверка питания, всей модели ACL и конкретного deployment остается отдельной.

## Командная строка

```powershell
telegram-patterns backup-sqlite live.sqlite snapshot-001.sqlite --source-root C:/service-state --target-root C:/service-backups --deadline-seconds 30 --json
telegram-patterns restore-sqlite-new snapshot-001.sqlite recovered-001.sqlite --source-root C:/service-backups --target-root C:/service-recovery --deadline-seconds 30 --json
```

`--target-root` соответствует Python-параметру `destination_root`. Успешный JSON
содержит хеш, размеры и признаки публикации/синхронизации/очистки, без исходных
путей. `--json` допустим для явного выбора формата; эти команды всегда используют JSON.

| Exit code | Результат |
| --- | --- |
| 0 | Новый файл опубликован; проверьте `directory_synced` и `cleanup_complete` |
| 2 | Отказ: аргументы, права, путь, существующая цель, поврежденная БД или другая безопасная ошибка |
| 3 | Занятая БД или исчерпанный бюджет |
| 4 | `publication-unknown`: публикация могла завершиться до последующей ошибки |
| 130 | Операция прервана пользователем |

При `publication-unknown` сначала проверьте наличие и целостность цели.
Не удаляйте существующий файл и не выдавайте новую операцию под видом повтора.
При аварии до публикации может остаться временный каталог, но частичный снимок
не должен приниматься за готовую цель.

## Проверка восстановления и переключение

После восстановления проверьте схему и прикладные инварианты под совместимой
версией приложения: исходные ID операций, ревизии, оплаченные периоды,
состояния `pending`/`sending`/`unknown` и незавершенные изменения.
Восстановленная копия не является доказательством, что внешняя операция
не произошла после времени снимка. Не очищайте неизвестный исход, не меняйте
его ID и не отправляйте автоматически оплату, возврат, уведомление или задачу.

Даже `pending` в старом снимке не доказывает отсутствие внешнего эффекта:
он мог произойти в исходном сервисе уже после копирования. До сверки держите
исходящие workers и финансовые записи выключенными. При polling старый
локальный журнал не возвращает уже подтвержденные Telegram updates:
подтверждение `getUpdates` происходит на стороне Telegram.

Восстановление может вернуть ранее отозванную сессию, старую роль или доступ.
До приема HTTP/бот-трафика отзовите восстановленные сессии средствами приложения,
а роли, операторские полномочия и оплаченный доступ подтвердите по текущему
доверенному источнику. Успешный `integrity_check` не проверяет эти права.
Компонент копирует данные и не выполняет такую прикладную подготовку автоматически.

Публичный пример `ref.core_sqlite_recovery` открывает настоящий WAL, делает
снимок и восстановление, затем через `SQLiteOutbox` подтверждает прежние ID,
ревизию и `unknown`; новый `claim` отсутствует. Это API-reference ID,
а не cookbook ID для `run-recipe`.

Компонент не заменяет живую БД, не меняет конфигурацию и не запускает сервис.
После проверок владелец отдельно планирует остановку всех writers, сверку
внешних эффектов, переключение на новый путь, health/readiness и пользовательский
сценарий. Автоматического переключения, миграции бизнес-схемы, возврата данных
поверх текущей БД и возобновления неизвестных отправок здесь нет.

## Источники и предел проверки

5 ноября 2026 сверены только используемые контракты:
[Python 3.13 Connection.backup](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.Connection.backup),
[SQLite Online Backup API](https://www.sqlite.org/backup.html),
[integrity_check](https://www.sqlite.org/pragma.html#pragma_integrity_check) и
[foreign_key_check](https://www.sqlite.org/pragma.html#pragma_foreign_key_check).
Отдельно сверено серверное подтверждение
[getUpdates](https://core.telegram.org/bots/api#getupdates); остальные разделы
Bot API этой проверкой не переаттестованы.
Проверки Windows с реальными файлами, WAL и авариями не заменяют независимый
POSIX-прогон, испытание потери питания или приемку рабочего хостинга.
