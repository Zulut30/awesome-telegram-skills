# Состояние Mini App: чтение, черновик и неизвестная операция

Термины: **неизвестный результат** — запрос мог выполниться, но ответа нет (таймаут, обрыв связи); повторять вслепую нельзя, сначала сверка; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

`ScopedAsyncState` управляет чтением и кешем в памяти, `SelectionDraftStore` — допустимыми полями черновика, `PendingOperationStore` — отдельной ссылкой на уже отправленную операцию. Эти экспериментальные API не создают сервер, не подтверждают личность и не добавляют офлайн-очередь платежей или новый мост Telegram. Существующие `ApiClient` и адаптеры фреймворков сохраняются. Установка скилла не устанавливает исполняемый пакет; подключение локального wheel/tarball описано в каноническом `docs/for-agents.md` репозитория.

## Чтение без устаревших ответов

```ts
import {ScopedAsyncState, type ApiClient} from '@awesome-telegram/patterns';

type Order = {readonly id: string; readonly status: string};
const reads = new ScopedAsyncState<Order>({maxEntries: 32});

async function loadOrder(client: ApiClient, verifiedScope: string,
                         decodeOrder: (value: unknown) => Order) {
  reads.setScope(verifiedScope); // Только scope из проверенной backend session.
  const result = await reads.read('order', ({signal}) =>
    client.request('/api/order', decodeOrder, {signal}));
  if (result.status === 'ready') return result.value;
  if (result.status === 'failed') return result.error; // Без raw exception/payload.
  // stale: запрос заменен, отменен или принадлежал прежнему аккаунту; UI не обновлять.
}
```

`snapshot(key)` возвращает `idle`, `loading`, `ready` с `value` или `failed` с безопасным `ErrorReport`. Для одного ключа побеждает последнее начатое чтение; разные ключи независимы. Предыдущее чтение получает сигнал отмены, а результат дополнительно проверяется по номеру поколения, даже если сетевой слой игнорирует сигнал. Отмененное чтение завершается как `stale`, не дожидаясь ответа; поздний успех или отказ обрабатывается и не меняет кеш.

Снимок и DTO отделены от загруженных данных и глубоко защищены от изменений. В кеш допускаются только JSON-значения: скаляры, `null`, плотные массивы и обычные объекты. Геттеры, экземпляры классов, циклы, `undefined` и неконечные числа отклоняются. Лимит копии — 10000 узлов и глубина 64. Это границы корректности и памяти, не замер производительности. `maxEntries` — целое 1–512, по умолчанию 32; при переполнении старейший ключ удаляется, его незавершенное чтение отменяется. Компонент не назначает срок свежести серверным данным: приложение показывает их давность, когда это влияет на решение, и явно обновляет чтение.

`cancel(key)` удаляет состояние одного чтения, `clear()` удаляет весь кеш и помечает старые результаты как `stale`. `dispose()` дополнительно сбрасывает область аккаунта и запрещает новые чтения и `setScope`; повторный вызов допустим. Хранилище не создает обработчики DOM/Telegram, таймеры или цикл подписок. Приложение управляет собственными подписками и навигацией. Отмена чтения не откатывает серверную запись; этот компонент предназначен для чтений.

## Смена аккаунта и токена

При смене аккаунта сначала удалите токен из памяти, очистите видимые личные заказ и корзину, вызовите `setScope(null)`. После серверной проверки новой `initData` сохраните новый токен в памяти и вызовите `setScope(session.scope)`. Не передавайте `initDataUnsafe.user.id` как доказательство проверки: наличие Telegram SDK само по себе не устанавливает личность.

Любое изменение области аккаунта синхронно очищает кеш и чтения, включая выход из аккаунта и повторный вход в него. Повторный `setScope` с той же строкой не очищает кеш: обновление токена того же пользователя не означает смену аккаунта. Результаты проверяются после каждого прикладного `await`; одной отмены сетевого запроса недостаточно, если чтение завершилось до смены аккаунта.

Не переносите ключи старого черновика и незавершенной операции в область нового аккаунта. Данные прежнего пользователя могут оставаться в его хранилище восстановления, но новая сессия не должна их показывать или отправлять. Разделение `localStorage` по аккаунтам не авторизует запросы: сервер на каждом действии проверяет токен и владельца объекта.

## Версии и TTL черновика

Прежний конструктор `SelectionDraftStore(storage, {namespace,scope,ttlMs,now?})`, схема 1 и ключ `tg-selection:<namespace>:<scope>:v1` сохранены. Разрешены только `serviceId`/`slotId`; данные авторизации, контакты, цена, подтверждения и идентификаторы операций не копируются.

Для новой схемы миграция задается явно:

```ts
const draft = new SelectionDraftStore(() => localStorage, {
  namespace: 'booking', scope: session.scope, ttlMs: 15 * 60_000,
  schemaVersion: 2,
  migrateFrom: {
    1: value => {
      const old = value as {serviceId: unknown; slotId: unknown};
      // Итог повторно проверяется встроенным allowlist/ID validator.
      return {serviceId: old.serviceId as string | null,
              slotId: old.slotId as string | null};
    },
  },
});
```

`migrateFrom` перечисляет только известные меньшие версии и функцию разбора каждой прежней структуры. Хранилище не сканирует неизвестные версии или чужие аккаунты. Принадлежность записи текущему аккаунту и исходный срок проверяются до разбора. После миграции срок равен минимуму прежнего срока и текущего `now+ttlMs`: чтение старых полей не продлевает их жизнь. Новая запись сохраняется до удаления прежней. При ошибке разбора или записи прежние данные остаются, возвращается `corrupt`/`unavailable`. После устранения переполнения хранилища миграцию можно повторить.

`clear()` удаляет текущую и все явно известные прежние копии данного аккаунта, чтобы старый черновик не появился вновь. При ошибке удаления возвращается `false`. Просроченные поля не восстанавливаются, даже если физическое удаление невозможно. Прежняя политика схемы 1 сохранена: поврежденный текущий черновик очищается. Это правило не распространяется на указатель незавершенной операции.

## Отдельный указатель незавершенной операции

```ts
const pending = new PendingOperationStore(() => localStorage, {
  namespace: 'booking', scope: session.scope,
});
const saved = pending.reserve(crypto.randomUUID());
if (saved.status === 'blocked') {
  // Corrupt/unsupported/unavailable storage: новый dispatch запрещен.
} else if (saved.status === 'existing') {
  // Сверить saved.value.operation на сервере; не отправлять новый intent с этим ID.
} else {
  // Pointer сохранен до отправки; backend должен поддерживать этот scoped opID.
}
```

Указатель содержит только UUID v4, `createdAt` и `pending|unknown` в отдельном `tg-pending:<namespace>:<scope>:v1`. Данные запроса, токен, `initData` и платежное подтверждение не сохраняются. При неизвестном исходе вызовите `markUnknown(originalID)`. Повторный `reserve` возвращает прежний ID, даже если вызывающий код предложил новый UUID. Это сигнал сверки прежнего намерения, а не разрешение отправить новые данные под старым ключом.

Срок жизни черновика и его очистка не удаляют указатель и не подтверждают отмену серверной операции. `complete(originalID)` допускается только после подтвержденного результата сервера; неверный ID не меняет запись. При ошибке записи или удаления возвращается `false`/`blocked`. `read()` различает `missing`, `restored`, `corrupt`, `unsupported`, `unavailable`. Поврежденная запись или неизвестная схема сохраняется и блокирует новую операцию; автоматической очистки неизвестного исхода нет.

Указатель не продлевает окно дедупликации сервера или провайдера. Когда сервер уже не может подтвердить прежний исход, нужен предусмотренный продуктом путь неопределенности или обращение к оператору. Очистка хранилища браузера пользователем или ОС уничтожает локальную ссылку; серверный список своих объектов и другой способ восстановления обеспечивает продукт.

Компонент рассчитан на одного владельца: `localStorage` не предоставляет межвкладочную атомарную транзакцию `read → reserve`. Две независимые вкладки могут предложить разные идентификаторы намерения; единственное выполнение в такой гонке не гарантируется. Приложение назначает одного отправителя либо резервирует намерение на сервере. Идемпотентность, права и неизменность данных проверяет сервер, а не хранилище браузера.

## Композиция магазина

Новый `examples/shop/frontend/src/domain-state.ts` отделяет сессию, корзину, заказ и указатель операции от интерфейса и глобальных объектов Telegram. `ShopOrderReader` получает функции отправки и разбора; запросу передаются неизменяемая копия сессии и сигнал отмены. Композиция с существующим сгенерированным клиентом магазина:

```ts
const state = new ShopDomainState(() => localStorage, {
  operation: (session, operation, signal) => {
    const client = new ApiClient({baseUrl: location.origin,
      headers: () => ({Authorization: 'Bearer ' + session.token})});
    return callApi(client, 'getOperation', {params: {operation}, signal});
  },
});
state.setSession(backendSession);
```

Смена аккаунта или выход очищает видимые корзину, заказ и кеш чтений до применения ответа нового аккаунта; повторный вход в тот же аккаунт сохраняет его указатель. `reconcile()` читает только сохраненную операцию, проверяет совпадение ее ID с серверным DTO и поколение аккаунта после `await`. `completeOrder` разрешен лишь для уже сверенного точного ID. Снимок не содержит токена. `dispose()` идемпотентен и очищает личность и состояние в памяти.

Текущий `main.ts` магазина не подключен к этому примеру без интерфейса и не переписан. Автоматическое обновление сессии, история и закрытие окна в браузере/Telegram, внедрение нового состояния во все экраны остаются отдельной интеграцией; наличие класса не закрывает целиком пункты 46–50. Ротация и отзыв серверной сессии, локальная приемка aiohttp/SQLite описаны в каноническом `docs/internal/shop-backend-production-contract.md` репозитория.

## Проверка

`npm test -w @awesome-telegram/patterns` собирает пакет, выполняет тесты Node и строгую проверку типов с положительными и отрицательными примерами, включая `packages/typescript/tests/types/async-state.ts`. Сохраняются проверки прежних API клиента, моста и черновика.

Отдельная проверка в настоящем браузере (Chrome или `CHROME_PATH`):

```powershell
npm.cmd run build -w @awesome-telegram/patterns
node_modules/.bin/tsc.cmd -p examples/shop/frontend/tsconfig.json --outDir output/production-run-2026-11-05/mini-app-state/domain
node packages/typescript/tests/async-state-browser.mjs
```

Она использует настоящие `fetch`, `localStorage`, перезагрузку страницы, локальный HTTP-сервер того же источника и собранную логику магазина. Проверяются устаревшие ответы, отмена запроса, изоляция кеша и аккаунтов, миграция и сроки, восстановление указателя после перезагрузки, сверка заказа и смена аккаунта между завершением чтения и продолжением обработки. Удаление последней проверки поколения аккаунта в отдельной игнорируемой собранной копии обнаруживается той же браузерной проверкой; исходный код для этой мутации не меняется.

Артефакты локального запуска: игнорируемый каталог `output/production-run-2026-11-05/mini-app-state/`. Проверки исходников, сборки и Chrome не равны приемке установленного tarball или полной поставки. Эта фикстура не подтверждает реальные клиенты Telegram, физические устройства, клавиатуру/экранный диктор, живую серверную личность или платежи.

Сверено 5 ноября 2026: [HTML Web storage](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute) — общее хранилище одного источника без предполагаемой блокировки; [Storage.setItem](https://developer.mozilla.org/en-US/docs/Web/API/Storage/setItem) — отказ при исчерпании квоты; [AbortController.abort](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort) — отмена запроса и чтения тела/потоков. Поколения аккаунта, разрешенные поля, сроки, миграции и указатель восстановления — явный контракт библиотеки, а не встроенные гарантии Telegram.
