# Platega: точки интеграции

Проверено 2 октября 2026 года по официальной документации.

| Операция | Документированный маршрут |
| --- | --- |
| [Авторизация](https://docs.platega.io/) | Base `https://app.platega.io/`; `X-MerchantId`, `X-Secret` |
| [Создание платежа](https://docs.platega.io/создание-платежной-ссылки-с-заданным-методом-29203843e0) | `POST /transaction/process`; paymentMethod, paymentDetails, payload; ответ transactionId и redirect |
| [Сверка статуса](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0) | `GET /transaction/{id}` |
| [Callback](https://docs.platega.io/callback-об-изменении-статуса-транзакции-29209725e0) | Заголовки `X-MerchantId`, `X-Secret`; HTTPS endpoint из настроек магазина |
| [Отмена/возврат](https://docs.platega.io/отмена-транзакции-38225949e0) | `POST /transaction/{id}/cancel`; предварительно проверить cancel-supported |
| [SDK](https://docs.platega.io/sdk-1991993m0) | Поставщик публикует Python, Node.js, PHP варианты |

Callback states: `CONFIRMED`, `CANCELED`, `CHARGEBACKED`; сопоставьте их со своей моделью. Shared secret headers сравнивайте безопасно, скрывайте их в логах. Схема отличается от HMAC Crypto Pay.

`metadata.userId` может требоваться для категории магазина. Не предполагайте единые тестовые credentials.

Ответ отмены может требовать дальнейшего контроля. Завершение возврата подтверждайте отдельным состоянием, а не HTTP 200 самого запроса.

## Рекуррентные СБП-подписки

Если нужны подписки, прочитайте отдельные [создание](https://docs.platega.io/создать-подписку-40029698e0), [получение](https://docs.platega.io/получить-подписку-40029717e0), [отмену](https://docs.platega.io/отменить-подписку-40029730e0) и [callback списания](https://docs.platega.io/callback-по-списанию-40029713e0); сверено 3 октября 2026 года. Создание использует `POST /transaction/process` в режиме Subscription, но еще не создает денежную транзакцию. Поле `transactionId` из этого ответа связывает созданную подписку; храните subscription ID отдельно от идентификаторов последующих списаний.

Состояние подписки запрашивается через `GET /subscription/{subscriptionId}`, будущие списания отменяются через `POST /subscription/{subscriptionId}/cancel`. Активация привязки сама по себе не выдает оплаченный период. Отмена продления и возврат конкретного списания — разные действия; оплаченный доступ меняется по модели продукта.

Callback списания имеет отдельный `Id`, связь `SubscriptionId` и `NextChargeAt`. Проверяйте shared-secret headers, статус, сумму, валюту и связь с локальным заказом; dedup/выдача привязаны к конкретному списанию, а не только к подписке. Проверьте два последовательных оплаченных периода одной подписки: оба списания учитываются, повтор одного не удваивает выдачу. Не смешивайте регистр/схему этого тела с обычным transaction adapter.

[Callback статуса подписки](https://docs.platega.io/callback-по-статусу-подписки-40030962e0) — отдельная ветка; тело повторно получено 3 октября 2026 года. Здесь `Id` равен `SubscriptionId`, это идентификатор подписки, а не списания. Опубликованный пример содержит `Status: SUBSCRIPTION_ACTIVATED`, `Amount`, `Currency`, `PaymentMethod`, `Payload` и `NextChargeAt`; сумма в таком событии не подтверждает оплату периода.

Разделяйте обработку статуса подписки и денежного списания даже при похожем JSON. Не используйте один subscription ID как уникальный ID всех смен статуса: разные события одной подписки имеют тот же `Id`. При нарушении порядка сверяйте текущее состояние через API. Полный перечень статусов и условия каждого перехода проверьте по актуальной схеме перед реализацией.
