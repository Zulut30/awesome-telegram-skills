# Транзакции, повторы и миграции

Термины: **outbox** — события, сохраненные в той же транзакции, что и изменение данных; отдельный обработчик выполняет их позже.

## Одна прикладная операция

В одной транзакции проверяйте допустимый переход, меняйте объект и сохраняйте необходимый durable результат. Конкурентность закрывают constraints, условное обновление, locking или isolation level по правилам выбранной БД. Check-then-insert без ограничения БД допускает гонку.

Идемпотентный ключ имеет область: principal/tenant, операция и ключ; необходимы политика срока хранения и проверка соответствия исходному payload. Тот же ключ с другим значимым запросом отклоняется явной ошибкой, а не возвращает случайный старый результат. Повтор возвращает сохраненный результат по контракту, включая прежний идентификатор.

Проверяйте текущие права перед replay результата. Результат и business change должны сохраняться согласованно; reservation ключа до незафиксированной операции не должна навсегда блокировать повторы. После потери ответа клиент повторяет тот же смысл/ключ либо запрашивает статус; сетевой timeout не доказывает отсутствие commit.

Пример для бронирования: один слот — ограничение БД; один подтвержденный заказ и результат повтора — транзакция; уведомление — outbox запись в той же транзакции, если доставка необходима. Отправка в Telegram после commit может провалиться отдельно: ответ API не должен утверждать доставку без подтверждения.

## Внешний эффект

Транзакция БД не откатывает уже отправленное сообщение или списание внешнего провайдера. При длительной интеграции сохраняйте состояние операции, ключ провайдера при его поддержке и процедуру выяснения результата. Outbox гарантирует надежность задания, но сама по себе не обеспечивает exactly-once отправку в сторонний API.

Избегайте удержания DB locks во время медленного сетевого вызова. Согласуйте промежуточные состояния/компенсацию с правилами операции. Автоматический retry применим только к известным безопасным случаям.

## Сессии и данные

В SQLAlchemy AsyncSession используется отдельно для каждой конкурентной задачи. Закрывайте session и возвращайте connection; для конкретной версии проверьте rollback, expiration и загрузку relations. Не передавайте request session в worker после завершения HTTP-запроса.

Деньги храните в подходящем точном представлении вместе с валютой; сериализованный decimal/units contract должен совпадать с frontend. Для времени различайте UTC instant, локальный календарный день и IANA timezone услуги. Сервер определяет цену и разрешенный слот, даже если клиент прислал другие значения.

## Проверка изменения схемы

Autogenerate дает кандидат миграции: проверьте, не превратилось ли переименование в удаление и создание, заполнение существующих строк, ограничения NULL и уникальности и реальные данные. Большую миграцию разделяйте на совместимые шаги только при необходимости релиза. Возможность rollback не предполагается: покажите recovery/backup требования выбранного изменения.

Проверьте fresh install и upgrade во временной БД, ограничения после миграции, сохранность данных и конкурентные запросы на отдельных соединениях. SQLite probe не подтверждает isolation/locking PostgreSQL; in-memory dictionary не подтверждает durable storage.
