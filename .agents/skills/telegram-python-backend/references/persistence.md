# Транзакции, повторы и миграции

## Одна прикладная операция

В одной транзакции проверяй допустимый переход, меняй объект и сохраняй необходимый durable результат. Конкурентность закрывают constraints, условное обновление, locking или isolation level по правилам выбранной БД. Check-then-insert без ограничения БД допускает гонку.

Идемпотентный ключ имеет область: principal/tenant, операция и ключ; необходимы политика срока хранения и проверка соответствия исходному payload. Тот же ключ с другим значимым запросом отклоняется явной ошибкой, а не возвращает случайный старый результат. Повтор возвращает сохраненный результат по контракту, включая прежний идентификатор.

Проверяй текущие права перед replay результата. Результат и business change должны сохраняться согласованно; reservation ключа до незафиксированной операции не должна навсегда блокировать повторы. После потери ответа клиент повторяет тот же смысл/ключ либо запрашивает статус; сетевой timeout не доказывает отсутствие commit.

Пример для бронирования: один слот — ограничение БД; один подтвержденный заказ и результат повтора — транзакция; уведомление — outbox запись в той же транзакции, если доставка необходима. Отправка в Telegram после commit может провалиться отдельно: ответ API не должен утверждать доставку без подтверждения.

## Внешний эффект

Транзакция БД не откатывает уже отправленное сообщение или списание внешнего провайдера. При длительной интеграции сохраняй состояние операции, ключ провайдера при его поддержке и процедуру выяснения результата. Outbox гарантирует надежность задания, но сама по себе не обеспечивает exactly-once отправку в сторонний API.

Избегай удержания DB locks во время медленного сетевого вызова. Согласуй промежуточные состояния/компенсацию с правилами операции. Автоматический retry применим только к известным безопасным случаям.

## Сессии и данные

В SQLAlchemy AsyncSession используется отдельно для каждой конкурентной задачи. Закрывай session и возвращай connection; для конкретной версии проверь rollback, expiration и загрузку relations. Не передавай request session в worker после завершения HTTP-запроса.

Деньги храни в подходящем точном представлении вместе с валютой; сериализованный decimal/units contract должен совпадать с frontend. Для времени различай UTC instant, локальный календарный день и IANA timezone услуги. Сервер определяет цену и разрешенный слот, даже если клиент прислал другие значения.

## Проверка изменения схемы

Autogenerate дает кандидат миграции: проверь rename против drop/create, backfill, nullable/unique constraints и реальные данные. Большую миграцию разделяй на совместимые шаги только при необходимости релиза. Возможность rollback не предполагается: покажи recovery/backup требования выбранного изменения.

Проверь fresh install и upgrade во временной БД, ограничения после миграции, сохранность данных и конкурентные запросы на отдельных соединениях. SQLite probe не подтверждает isolation/locking PostgreSQL; in-memory dictionary не подтверждает durable storage.

Источники: [конкурентные AsyncSession](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks), [PostgreSQL ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html), [Alembic autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).
