# Кеш, операции и восстановление

| Состояние | Допустимое действие |
| --- | --- |
| Локальный черновик | Редактировать и восстановить допустимые поля; это еще не заказ |
| Кеш чтения | Показать с оговоркой давности, обновить по необходимости |
| Не отправлено | Отправить после проверки сессии/условий, если сценарий разрешает |
| Отправлено, ответ потерян | Сверить стабильный operation ID/серверный объект; не считать отмененным |
| Подтверждено сервером | Показать серверный результат, убрать pending запись |
| Конфликт/истекло | Сохранить допустимый ввод, предложить согласованное исправление |

## Контракт операции

Пример записи бронирования: `(owner_id, operation_id)` уникален в backend, запись содержит hash семантического payload и результат. Тот же ключ с другим payload отклоняется; одинаковая операция возвращает прежний результат. Срок серверной dedup защиты должен покрывать разрешенное клиентом время восстановления. Внешний provider может иметь другое окно идемпотентности.

После потерянного ответа прочитайте сохраненную операцию. Неизвестность без пути сверки требует явной политики разбора/повтора, а не нового ID. Не перечисляйте чужие операции: право на чтение результата проверяется сервером.

Для offline outbox минимально нужны owner scope, ID, payload/version, created/expiry, состояние и результат. Смена пользователя блокирует чужую запись. Несколько вкладок/повторный mount не должны создавать независимых отправителей; даже при конкуренции backend сохраняет инвариант. Между network и локальным storage общей транзакции нет.

Срок хранения личных полей черновика и срок восстановления отправленной операции — разные ограничения. Если ответ потерян, не удаляйте единственную связь с операцией вместе с expired form record. Минимальный допустимый scoped recovery pointer может содержать operation ID, время/состояние и reference серверного объекта без контактов, токенов и исходного payload. Возможен серверный путь восстановления вместо local pointer.

После удаления полей сначала сверяйте операцию, прежде чем разрешить новую отправку того же намерения. Retention pointer не продлевает серверное/provider окно dedup: когда прежний результат уже нельзя надежно определить, нужен явный unresolved путь, а не автоматический повтор или хранение личных данных навсегда. Если storage не позволяет сохранить recovery state, не обещайте восстановление после закрытия; используйте доступный серверный путь либо объясните ограничение.

Отмена до начала dispatch подавляет отправку через согласованную границу. После отправки отмена локального job не отменяет серверный эффект; для этого нужен отдельный контракт продукта.

## Storage и конфликты

IndexedDB полезна для структурированного черновика, но операция записи успешна после завершения транзакции, а не только отдельного request. Проверяйте реальную availability; не обещайте сохранность после очистки данных/удаления приложения.

Telegram DeviceStorage/SecureStorage подключаются по client/version gate и необходимости. Они не создают серверную личность и не делают любые данные пригодными для хранения. Service Worker допускается только после проверки среды; работа всего приложения offline не следует из сохраненного черновика.

Для редактирования серверного объекта используйте revision/ETag или уже выбранный контракт конфликтов. При изменении цены/слота не отправляйте старый выбор молча; обновите обзор и получите необходимое подтверждение.

Источники сверены 3 октября 2026 года: [IndexedDB transactions](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB), [online hint](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine), [Telegram storage API](https://core.telegram.org/bots/webapps). Operation ledger и outbox — архитектурные варианты продукта, не встроенные гарантии Telegram.
