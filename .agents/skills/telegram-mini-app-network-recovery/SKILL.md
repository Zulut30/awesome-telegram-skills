# Восстановление сети и черновиков

Определите, что продукт действительно разрешает делать без связи. Сохраняйте существующий HTTP/store слой; очередь offline-записей, Service Worker и отдельная библиотека не обязательны. При узком исправлении timeout не внедряйте полный offline режим.

## Данные и состояния

Для границ cache/outbox и повторов прочитайте [references/recovery.md](references/recovery.md). Различайте локальный черновик, кеш чтения, pending запрос и подтвержденный серверный объект. Cached экран сообщает давность там, где она влияет на решение.

Храните только допустимые данные с account/tenant scope, сроком хранения и версией схемы. Обработайте недоступность storage, quota и поврежденный черновик без падения приложения. Logout/смена аккаунта изолируют кеш и запрещают отправку старого черновика под новой личностью.

Разделяйте срок хранения полей черновика и ссылку на уже отправленную операцию. Истечение TTL контактов не подтверждает ее отмену и не разрешает новый operation ID для слепого повтора; сохраните минимальный допустимый путь сверки либо явное unresolved состояние.

`navigator.onLine` — подсказка, не доказательство доступности API. Проверяйте реальный исход запроса; повторный background/foreground может требовать новой сессии и актуальных прав. Не сохраняйте initData/bearer tokens в черновиках.

## Повторы

Чтение повторяйте ограниченно по типу ошибки, сроку и retry_after. Cancel и смена выбора прекращают ненужный запрос; старый ответ не заменяет новый. 401, запрещенная операция и конфликт данных требуют своих действий, а не бесконечного retry.

Для записи используйте стабильный scoped operation ID и неизменный payload, если backend имеет соответствующий контракт. Timeout означает неизвестный результат: сначала сверяйте операцию/объект, затем действуйте по политике проекта. UI-кнопка retry сама не обеспечивает идемпотентность.

Не ставьте оплату, возврат или необратимое действие в автоматическую offline очередь по умолчанию. При разрешенной отложенной записи покажите статус, возможность отмены до dispatch и необходимость свежей проверки сервером.

## Проверка

Воспроизведите потерю связи до отправки и после серверного commit, повторное открытие, истечение сессии/TTL черновика, конфликт версии и смену аккаунта. Проверьте сохранение допустимого ввода, сверку неизвестной операции после удаления полей и один прикладной эффект при повторе.

Для реализации выполните typecheck/build и наблюдаемый frontend/API сценарий. Fake network и browser storage проверяют свой scope; они не подтверждают Telegram WebView storage или реальный backend, если тот не участвовал.
