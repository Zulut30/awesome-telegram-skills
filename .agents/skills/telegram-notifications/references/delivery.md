# Надежная отправка

Термины: **outbox** — события, сохраненные в той же транзакции, что и изменение данных; отдельный обработчик выполняет их позже; **неизвестный результат** — запрос мог выполниться, но ответа нет (таймаут, обрыв связи); повторять вслепую нельзя, сначала сверка; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

## Задание и claim

Сохраняйте job/campaign id, recipient, событие-основание, scheduled_at, срок полезности и состояние. Уникальный logical key предотвращает повторное создание одного задания. Claim/lease и переходы реализуются атомарно в выбранном storage; worker другого процесса не полагается на локальный lock.

Outbox может согласовать задание с изменением заказа в одной транзакции. Sender живет отдельно; успешный commit заказа не означает отправку уведомления. Перед dispatch проверяйте активность кампании, подписку, доступность получателя и актуальность содержимого. Отписка, уже случившаяся до этого этапа, подавляет отправку; запрос, уже принятый Telegram, невозможно отозвать одной отменой очереди.

Определите атомарную границу начала отправки: перед HTTP-вызовом проверьте актуальные eligibility/version и право worker на claim, затем переведите job в `dispatching`. Cancel/optout должны сериализоваться с этим переходом. Если отмена победила — подавите задание; если попытка уже началась — результат отмены допускает текущую отправку. Между commit и внешним API нет общей транзакции: не обещайте остановку только потому, что Telegram еще не вернул ответ, и не держите DB-транзакцию открытой на время сети.

Lease должен покрывать попытку или продлеваться по правилам worker. После crash не считайте любое in-flight задание безопасным для повтора. Зафиксируйте начало попытки и идентификатор/результат ответа, если он известен.

## Ответы и неизвестность

| Наблюдение | Действие |
| --- | --- |
| Успех с Message | Сохраните message_id/завершение по контракту; не приравнивайте к прочтению |
| 429 с retry_after | Отложите не раньше указанного срока; согласуйте ограничения chat/бота и другие workers |
| Явная временная ошибка | Ограниченный retry с backoff/jitter, attempts и сроком полезности |
| Явно недоступный получатель/постоянная ошибка | Terminal/suppressed согласно конкретной причине; без бесконечного retry |
| Timeout/disconnect после отправки | Outcome может быть неизвестен: API мог уже принять сообщение |

Для sendMessage нет общего application idempotency key. Локальный dedup, lease и outbox не обещают exactly-once Telegram delivery при потерянном ответе. Выберите политику unknown outcome по последствиям сообщения: сверка где реально доступна, ручное решение либо ограниченный повтор с признанным риском дубля. Не придумывайте API поиска исходящего сообщения по произвольному job id.

Используйте существующий обработчик очереди или планировщик в БД, если он подходит. Для малого сервиса не обязательны Celery, Redis и Kafka; задания и попытки должны переживать рестарт. Метрики: возраст самого старого готового к отправке задания, отправлено, повторы, подавлено, окончательные отказы и неизвестный результат; логи без токена и полного текста.

Проверяйте гонки отдельными workers/соединениями и управляемым clock. Повтор кампании, новый logical event и retry одного задания — разные операции. Не включайте allow_paid_broadcast без авторизованного режима и расходов; актуальные лимиты и eligibility сверяйте перед интеграцией.
