# Надежная отправка

## Задание и claim

Сохраняй job/campaign id, recipient, событие-основание, scheduled_at, срок полезности и состояние. Уникальный logical key предотвращает повторное создание одного задания. Claim/lease и переходы реализуются атомарно в выбранном storage; worker другого процесса не полагается на локальный lock.

Outbox может согласовать задание с изменением заказа в одной транзакции. Sender живет отдельно; успешный commit заказа не означает отправку уведомления. Перед dispatch проверяй активность кампании, подписку, доступность получателя и актуальность содержимого. Отписка, уже случившаяся до этого этапа, подавляет отправку; запрос, уже принятый Telegram, невозможно отозвать одной отменой очереди.

Определи атомарную границу начала отправки: перед HTTP-вызовом проверь актуальные eligibility/version и право worker на claim, затем переведи job в `dispatching`. Cancel/optout должны сериализоваться с этим переходом. Если отмена победила — подави задание; если попытка уже началась — результат отмены допускает текущую отправку. Между commit и внешним API нет общей транзакции: не обещай остановку только потому, что Telegram еще не вернул ответ, и не держи DB-транзакцию открытой на время сети.

Lease должен покрывать попытку или продлеваться по правилам worker. После crash не считай любое in-flight задание безопасным для повтора. Зафиксируй начало попытки и идентификатор/результат ответа, если он известен.

## Ответы и неизвестность

| Наблюдение | Действие |
| --- | --- |
| Успех с Message | Сохрани message_id/завершение по контракту; не приравнивай к прочтению |
| 429 с retry_after | Отложи не раньше указанного срока; согласуй ограничения chat/бота и другие workers |
| Явная временная ошибка | Ограниченный retry с backoff/jitter, attempts и сроком полезности |
| Явно недоступный получатель/постоянная ошибка | Terminal/suppressed согласно конкретной причине; без бесконечного retry |
| Timeout/disconnect после отправки | Outcome может быть неизвестен: API мог уже принять сообщение |

Для sendMessage нет общего application idempotency key. Локальный dedup, lease и outbox не обещают exactly-once Telegram delivery при потерянном ответе. Выбери политику unknown outcome по последствиям сообщения: сверка где реально доступна, ручное решение либо ограниченный повтор с признанным риском дубля. Не придумывай API поиска исходящего сообщения по произвольному job id.

Используй существующий queue runner/DB scheduler, если он подходит. Для малого сервиса не обязательны Celery, Redis и Kafka; при restart нужно явно сохранить задания и попытки. Метрики: due/backlog age, sent, retry, suppressed, terminal и unknown; логи без токена/полного текста.

Проверяй гонки отдельными workers/соединениями и управляемым clock. Повтор кампании, новый logical event и retry одного задания — разные операции. Не включай allow_paid_broadcast без авторизованного режима и расходов; актуальные лимиты и eligibility сверяй перед интеграцией.
