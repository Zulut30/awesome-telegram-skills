# OIDC, сессия и account linking

Текущий протокол сверен 3 октября 2026 года по [Telegram Login](https://core.telegram.org/bots/telegram-login). Старый iframe widget с hash и Mini App initData не проверяются этим JWT алгоритмом. При миграции поддержите только явно нужный старый путь с его собственной проверкой.

## Конфигурация

Telegram публикует discovery `https://oauth.telegram.org/.well-known/openid-configuration` и JWKS `https://oauth.telegram.org/.well-known/jwks.json`. Issuer — `https://oauth.telegram.org`; audience сопоставляется с настроенным Client ID/Bot ID по документации. Не берите issuer/audience/redirect из произвольного параметра клиента.

RS256 используется по умолчанию; выбранный в BotFather алгоритм определяет allowlist verifier. Некоторые альтернативные algorithms ограничены scope: не расширяйте набор только по JWT header. Пример profile содержит отдельные sub и id; sub остается непрозрачной строкой identity. `id` для Bot API появляется при соответствующем scope и проверенной подписи. Отсутствие id не разрешает подставить числовой sub.

Отдельный UserInfo endpoint текущей документацией не предоставлен. OIDC библиотека должна уметь получать claims из проверенного ID token. Зафиксируйте установленную версию и особенности библиотечного callback.

## Login transaction

Храните короткоживущую server-bound запись: ожидаемые state/nonce, verifier, фиксированный callback, цель login/link и идентификатор сессии инициатора. Cookie политики учитывают способ возврата от провайдера; session cookie требует HttpOnly/Secure и защиту CSRF для применимых действий.

Проверяйте state до code exchange, не используйте успешный токен для подмененной link transaction. Полученный ID token проверяется библиотекой с доверенным JWKS, issuer, audience, exp, допустимым временем/nonce и обязательным sub. Одноразовость и конкуренция контролируются транзакцией/claim записи; неопределенный исход code exchange не означает разрешение бесконечно повторять его.

Проверка `audience=client_id` в JWT-библиотеке может проверять только вхождение Client ID в массив `aud`. По [OIDC ID Token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation) отклоняйте дополнительные аудитории, которым сервис явно не доверяет; список доверенных аудиторий берется из конфигурации, а не токена. Для обычного Telegram Login отправная политика — только настроенный Client ID. Проверяйте это поведение выбранной OIDC-библиотеки; проверка подписи JWT сама по себе не выполняет весь OIDC-контракт.

Если присутствует `azp`, проверьте authorized party по правилам выбранного flow/extensions; для этого входа не принимайте значение чужого Client ID. Наличие `azp` не является универсальным обязательным условием любого массива `aud`: текущий OIDC Core отдельно задает правила extensions и рекомендуемую проверку значения. Не объявляйте отсутствие `azp` ошибкой обычного документированного Telegram токена.

`kid` выбирает ключ из доверенного кеша. Неизвестный kid допускает ограниченное обновление JWKS; ошибку сети/неизвестный ключ обрабатывайте отказом, а не отключением подписи. Не делайте fetch по jku/x5u из токена.

При Login SDK popup учитывайте браузерную блокировку и COOP: `same-origin` может мешать обмену с popup. Меняйте только нужную конфигурацию, проверив требования проекта. OIDC redirect flow — возможная альтернатива, если подходит задаче.

## Привязка и тесты

Уникальная identity связывается с одним аккаунтом по модели сервиса. Проверенный Telegram вход не дает права присоединить ее к чужому local account ID из запроса. При конфликте не переноситесь автоматически по совпавшему телефону/username; покажите безопасный путь разрешения.

Проверьте login/link replay, одновременные link запросы, logout во время popup, незнакомый ключ и смену алгоритма; добавьте signed JWT с дополнительной недоверенной `aud` и чужой `azp`. Canary секреты не должны появиться в конечных логах/ответе. Синтетический signed JWT проверяет verifier, а live flow — реальную конфигурацию Telegram; эти доказательства различаются.

Дополнительный источник: [OIDC ID Token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation). Политики linking и собственной сессии определяются продуктом.
