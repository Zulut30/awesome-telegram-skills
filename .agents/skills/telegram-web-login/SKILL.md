# Telegram Login для сайта

## Когда использовать

Обычный сайт входит через Telegram: OIDC, проверка ID token на Python-сервере, привязка аккаунта сервиса.

## Когда не использовать

`initData` Mini App — telegram-mini-app-auth. Авторизация пользовательского клиента MTProto — telegram-user-client.

## Алгоритм

Определите текущую библиотеку аутентификации, домены, адрес возврата и нужные утверждения (claims) токена. Сохраняйте выбранный фреймворк; не добавляйте отдельный сервис идентификации без необходимости. Telegram Login не дает права читать чаты пользователя и не является initData Mini App.

### Протокол

Про текущий OIDC и привязку аккаунтов прочитайте [references/login.md](references/login.md). Используйте поддерживаемую OIDC-библиотеку либо официальный Telegram Login SDK — в зависимости от сценария. Сервер проверяет ID token до того, как доверять данным; декодированные данные пользователя из адреса возврата личность не доказывают.

Client Secret и обмен кода на токены остаются в Python-сервере. Разрешенные адреса и redirect URI должны совпадать с настройками приложения. В Authorization Code используйте одноразовый `state`, привязанный к серверной сессии, и PKCE S256; `nonce`, когда он применяется, привязывается к той же попытке входа. Срок действия и повторное использование контролирует сервер.

Проверяйте подпись, разрешенный в настройках алгоритм, издателя (`iss`), аудиторию (`aud`), срок действия (`exp`) и обязательные утверждения. Ключи берите из доверенного JWKS Telegram; адресу ключа из самого JWT доверять нельзя. Повторный вызов адреса возврата не создает вторую сессию или привязку. После входа используйте защищенную сессию сервиса по его существующей модели.

### Аккаунт сервиса

Храните OIDC-идентичность по паре `(issuer, sub)`; не принимайте `sub` за ID пользователя Bot API. Для связи с ботом проверяйте подписанный Telegram id, если он доступен, и его контракт. Username, имя, фото и телефон не служат ключом автоматического объединения аккаунтов.

Привязка требует подтвержденной текущей сессии сервиса и проверенного входа через Telegram. Конфликт с уже привязанной идентичностью обрабатывается явно; уникальность хранится в БД. Отвязка не должна лишать пользователя последнего способа восстановить доступ без согласованного решения.

Запрашивайте доступ к профилю, телефону и сообщениям от бота только по потребности. Разрешение на вход не заменяет отдельное разрешение на сообщения. Не пишите в журнал код авторизации, ID token, PKCE verifier, секреты или полный ответ провайдера.

## Проверка

Проверьте подписанный токен с неверными издателем, аудиторией и алгоритмом, истекший токен, несовпадение `state` или `nonce`, повторное использование и одновременную привязку к двум аккаунтам. Тестовые JWT подписывайте локальными ключами и явно отмечайте, что Telegram их не подписывал.

При реализации проверьте сборку сервера и сайта, отказ во всплывающем окне и ошибку на адресе возврата. Реальный вход требует тестовой настройки в BotFather; без нее опишите локальные проверки и оставшийся сквозной шаг.

## Типичные ошибки

- Данным пользователя из адреса возврата доверяют без проверки ID token на сервере.
- Client Secret и обмен кода на токены оказываются во frontend.
- `state` не привязан к серверной сессии, PKCE не используется.
- Ключ проверки берется по адресу из самого JWT, а не из доверенного JWKS.
- OIDC `sub` принимается за ID пользователя Bot API; аккаунты объединяются по username или телефону.
