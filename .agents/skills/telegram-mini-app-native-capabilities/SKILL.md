# Native-возможности Mini App

Определите нужный пользовательский сценарий, установленный SDK/bridge и целевые клиенты. Подключайте только требуемую capability. Сверьте точное имя, версию, callback/events и ограничения с текущей официальной документацией и API установленного SDK.

## Контракт адаптера

Для различий capabilities прочитайте [references/capabilities.md](references/capabilities.md). Проверяйте version gate и фактическую доступность метода/объекта; platform и наличие window.Telegram не доказывают поддержку. Подписки, состояние и cleanup принадлежат одному adapter.

Опишите состояния «недоступно», «ожидает действия», «запрос отправлен», «принято с результатом», «отказ или отмена» и «ошибка» в форме, подходящей конкретному API. Не сводите отказ пользователя и отсутствие функции к success. Переход в настройки/запрос выполняется по осмысленному действию пользователя там, где API этого требует.

## Результат и запасной вариант

После async callback проверьте, что экран/запрос и пользовательский контекст еще актуальны. Не применяйте результат старого запроса к новой форме. Сверьте ограничения повторного вызова и порядок init; не вызывайте запрос permission в бесконечном цикле.

Предусмотрите полезную альтернативу: ручной выбор адреса, стандартное поле ввода, доступную ссылку или объяснение. Fallback не должен незаметно менять контракт доверия и отправлять чувствительные данные в менее защищенное хранилище.

Серверные права и auth остаются серверными: геолокация, QR, biometric callback и local storage не доказывают личность или доступ к объекту. Ключи бота/провайдера не передаются клиенту даже для SecureStorage.

## Проверка

Через fake adapter проверьте unsupported, отказ, отмену, ошибку, success, повторный вызов и поздний callback после ухода. Затем проверьте фактическое поведение нужного API в целевом Telegram-клиенте с разрешенной тестовой операцией. Запишите отдельно mock и native evidence, версии и непроверенные клиенты.
