# Магазин: Mini App, заказ и Telegram Stars

Термины: квитанция (receipt) — сохраненная запись о выполненной операции; повтор возвращает ее вместо второго эффекта; **outbox** — события, сохраненные в той же транзакции, что и изменение данных; отдельный обработчик выполняет их позже; **неизвестный результат** — запрос мог выполниться, но ответа нет (таймаут, обрыв связи); повторять вслепую нельзя, сначала сверка; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

Пример пункта 018 связывает TypeScript-каталог и корзину с Python/aiohttp backend, настоящей SQLite и aiogram 3.31.0. Использует публичные `ApiClient`, `TelegramBridge`, `TelegramNativeAPI`, `createAppShell`, `validate_init_data`, `SQLiteOnce`, `stars_invoice` и `StubSession` библиотеки 0.27.0 (CI проверяет пример на текущей версии). Приложение `awesome-telegram-shop-example` 0.1.0 поставляется отдельно; его классы не public exports библиотеки.

Два учебных цифровых товара стоят 25 и 40 Stars. Backend принимает только IDs, operation UUID и согласие с версией условий. Цена и валюта фиксируются сервером в заказе; клиентские price/user_id/paid поля отклоняются. Данные запуска проходят HMAC/freshness проверку; сервер выдаёт сессионный токен на 10 минут, который frontend хранит только в памяти и передаёт в заголовке `Authorization: Bearer` (почему не cookie — ниже). В production требуются HTTPS и точный origin. `initDataUnsafe` не даёт прав. Каждое действие над заказом или материалом проверяет владельца из сессии и текущую серверную роль; роль из тела запроса не принимается.

Оплата проходит через Stars (`XTR`, пустой provider_token, один price). Счёт связан с owner-scoped заказом. Pre-checkout сверяет bot, пользователя, payload, сумму, валюту, состояние и доступ; ответ не выдаёт товар. Только trusted SDK `successful_payment` атомарно сохраняет receipt, paid и access. Повтор charge не выдаёт доступ второй раз. Второй charge или поздний платёж за уже купленный товар сохраняется для ручной сверки. Публичного HTTP receipt/grant endpoint нет. Invoice callback лишь запускает чтение статуса с backend.

## Рабочая конфигурация

После отдельной настройки BOT_TOKEN, проверки, что нет установленного webhook и другого получателя getUpdates, настройки обратного прокси с HTTPS, постоянного локального пути БД, ваших реальных условий и поддержки:

```powershell
& .\.venv\Scripts\telegram-shop-example.exe --database 'C:\shop-data\shop.sqlite' --frontend "$shopProject\frontend\dist" --origin 'https://shop.example.com' --terms 'C:\shop-data\terms.txt' --terms-version '2026-01' --support 'Ваш контакт и порядок обращения к оператору' --port 8080
```

Parent БД должен существовать. Runtime слушает только 127.0.0.1 за вашим HTTPS proxy, владеет OS lock до cleanup HTTP/FSM/session и запускает polling с надежным приемом до продвижения offset, без смены webhook/удаления updates. `/start` в личном чате открывает HTTPS Mini App, `/terms`, `/support`, `/paysupport` доступны пользователю. Production HTML подключает официальный WebApp SDK; обычный браузер показывает каталог и приглашение войти через Telegram. Согласие сохраняется с заказом. Учебные условия нельзя использовать как оферту рабочего магазина.

## Точки запуска и параметры

`launch.py` строит модели кнопки меню, inline- и reply-клавиатуры, ссылок `start`/`startapp` без вызовов сети. Владелец отдельно просматривает `launch_configuration` и применяет нужную кнопку меню; Main Mini App настраивается через BotFather. Runtime сам не меняет эту конфигурацию. `/start orders` в личном чате дает кнопку покупок, `/start catalog` — каталога. Неизвестный или слишком длинный параметр возвращает обычный каталог.

| Запуск | Поведение магазина |
| --- | --- |
| «Menu Button», «Main Mini App», встроенная кнопка `web_app` | При наличии проверяемой `initData` вход через тот же backend; параметры выбирают только экран |
| Reply-кнопка `web_app` | Без пользовательской `initData` доступен каталог; покупка заблокирована, предложен вход из поддерживаемого запуска |
| Inline mode | Отдельный от inline-кнопки способ; пустые данные запуска не дают личность или доступ |

`frontend/src/launch.ts` разрешает только `catalog`/`orders` из `start_param` либо `tgWebAppStartParam`; дубли, конфликт и неизвестные значения открывают каталог. Это подсказка навигации, не авторизация: даже измененный URL не задает пользователя, роль, цену или оплату. История хранит только экран; серверные права действуют на каждом запросе. Магазин использует HTTPS API, не подменяет его `sendData` или `answerWebAppQuery`. Локальные модели и профили запуска не доказывают применение настроек в настоящем Telegram.

Для самостоятельной проверки домена без DOM или Telegram после сборки frontend: `node --test examples/shop/frontend/tests/domain.test.mjs` из корня checkout. Те же пять проверок выполняются после установки tarball во внешний consumer помощником `verify_shop_example.py`; они проверяют чтение без автоматического POST, явный прежний запрос, смену условий/аккаунта, транспорт, параметры и завершение возвращенного заказа.

Источники точек запуска сверены 5 ноября 2026: [способы запуска Mini Apps](https://core.telegram.org/bots/webapps#implementing-mini-apps), [данные запуска](https://core.telegram.org/bots/webapps#webappinitdata), [ссылки на бота](https://core.telegram.org/bots/features#deep-linking). Проверена только эта часть документации; дата платежных контрактов ниже не меняется.

## Контракт API

`examples/shop/openapi.json` (OpenAPI 3.1) описывает все пятнадцать операций `/api/*`: тела запросов, ответы 200 и коды ошибок, bearer-сессию и операторский возврат. `python scripts/build_openapi_types.py` генерирует из него `frontend/src/api-types.ts`: интерфейсы схем, декодеры, которые проверяют ответ целиком (лишнее или отсутствующее поле, тип, перечисление), и `callApi(client, operationId, {params, body})` поверх `ApiClient` с методом и путем из контракта. Frontend вызывает backend только через `callApi`, поэтому расхождение ловится в трех местах: устаревший `api-types.ts` (`--check` в CI), код клиента, который не совпадает с новыми типами (`tsc`), и сервер, чьи маршруты или реальные ответы не совпадают с контрактом (тест `test_routes_and_responses_follow_the_openapi_contract`). Генератор принимает только проверяемое подмножество схем и отказывает, например, на `format` или открытый объект, чтобы в контракт не попало ограничение, которое клиент молча пропустит. Этот тест нашел реальную ошибку: повтор операции с другим составом отвечал 422 вместо 409, потому что `OperationConflict` перехватывался как `ValueError`.

## Сессия: заголовок вместо cookie

Telegram Web показывает Mini App во фрейме `<iframe>` своего сайта ([методы Mini Apps](https://docs.telegram-mini-apps.com/platform/methods)), поэтому для магазина это сторонний (cross-site) контекст. Cookie `SameSite=Strict` и `Lax` там не отправляются ([Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)); `SameSite=None` требует `Secure`, а сторонние cookie по умолчанию ограничивают Safari (ITP) и Firefox (Total Cookie Protection) ([third-party cookies](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies)). Прежняя cookie `SameSite=Strict` воспроизводимо ломала вход: в Chromium во фрейме с другого сайта `POST /api/session` возвращал 200, cookie не сохранялась, а `POST /api/orders` получал 401.

Поэтому `POST /api/session` возвращает `{token, scope, expires_in}`, а frontend держит токен в переменной модуля и отправляет `Authorization: Bearer <token>`. Браузер не прикладывает такой заголовок сам, поэтому отдельный CSRF-токен не нужен; запись дополнительно требует точный `Origin`. Токен не попадает в localStorage, sessionStorage и cookie; база хранит только его SHA-256. После reload или истечения 10 минут вход повторяется по initData (до часа с запуска). Главный риск такой схемы — XSS: CSP запрещает чужие скрипты, кроме официального SDK. Один способ работает во всех клиентах: в Desktop, iOS и Android Mini App открывается в WebView как страница верхнего уровня, но отдельная ветка для cookie там не нужна.

## Восстановление и границы

Bearer session хранится в памяти клиента, в SQLite — только hash, bot/actor и expiry. `POST /api/session` обменивает проверенную свежую initData на сессию на 600 секунд. `POST /api/session/rotate` с текущим bearer, точным `Origin` и JSON `{}` атомарно заменяет только эту сессию: старый token сразу недействителен, новый живет 600 секунд от rotation. `POST /api/session/revoke` с теми же заголовками и `{}` отзывает текущую сессию; повтор возвращает 401, остальные сессии устройства/пользователя сохраняются. Revoke не отменяет уже авторизованную in-flight операцию и не отзывает Telegram initData: владелец свежих подписанных данных может войти заново. Роль хранится на сервере отдельно от сессии. Обычная роль `customer` может покупать, `viewer` читает только собственные заказы и уже оплаченные материалы, `blocked` не имеет доступа к личным объектам. Наличие сессии не отменяет эти ограничения; отзыв своей сессии остается доступным.

При потерянном ответе ротации приложение заново обменивает свежую `initData` и проверяет тот же ID операции. Действующий `main.ts` использует `ShopDomainState`, отдельные `shop-api.ts` и `examples/shop/frontend/src/telegram-adapter.ts`: личность, корзина, согласие, заказ и связанные запросы отделены от отображения. Кнопки «Обновить вход» и «Выйти» вызывают серверные ротацию и отзыв. Возобновление окна обновляет сессию и сверяет заказ; одновременные события объединяются. При смене аккаунта старые токен, видимые заказ/корзина и кеш очищаются до нового входа. Поздний ответ прежней ротации или чтения не заменяет новую сессию. Прежний запрос остается под исходной серверной областью аккаунта и не переносится новой личности.

Корзина имеет отдельную схему и срок 15 минут: только ID товаров, условия и согласие, без цены, контактов или авторизации. Срок корзины не удаляет минимальный указатель операции и связанный неизменный запрос. Подтвержденная сервером оплата очищает соответствующее намерение и старую корзину. Нативная кнопка возврата и история браузера переключают одни и те же экраны; незавершенная работа включает подтверждение закрытия. Повторное монтирование сначала освобождает обработчики прежнего экземпляра. Все события SDK в локальной проверке синтетические: это не приемка реальных клиентов Telegram.

Все session/order mutations требуют единственный exact same-origin `Origin`; private GET допускает отсутствие Origin, но отвергает явно чужой. Сессия принимается только из единственного `Authorization: Bearer ...`, не cookie/query/body. CORS headers не выдаются; чужой preflight не открывает доступ. Строгий JSON parser отвергает duplicate fields, неизвестные поля и неверный Content-Type, общий body limit — 32768 bytes. Public catalog/policy/static остаются публичными; остальные маршруты заново проверяют bearer и object owner, никакой клиентский ID/роль/цена не дает полномочий.

Pending operation/cart/terms сохраняются под server-derived scope до POST, отдельно от любой TTL сессии. Если локальное сохранение недоступно, новый заказ не отправляется. Reload проверяет тот же operation ID; 404 только показывает кнопку «Повторить сохранённый запрос»: чтение и загрузка страницы не отправляют POST автоматически. Явное нажатие использует прежние ID, товары и условия; новая версия условий блокирует повтор, сервер заново проверяет роль и права. Theme, back и resize не пересоздают заказ. Corrupt pending блокирует новый checkout и предлагает историю покупок. Номера в localStorage не разрешают доступ; токен сессии и initData туда не записываются, после reload вход повторяется по initData.

Invoice проходит none → creating → ready. Timeout/invalid response/crash после вызова без сохранённой ссылки дают unknown; новая ссылка автоматически не создаётся. Такой заказ требует сверки. Сохраняется один accepted pre-checkout query на заказ: после неизвестной/прерванной предыдущей оплаты нельзя молча разрешать второй charge. Смена accepted query требует отдельной операторской сверки. Полный возврат конкретного Stars-платежа описан ниже; неизвестный исход счета не разрешает новый внешний вызов.

Схема SQLite версии 3 добавляет операторские полномочия и финансовые связи; переход с версий 1/2 сохраняет сессии, заказы, квитанции и доступ. Неизвестная версия отклоняется до изменения данных. Роли меняет доверенная конфигурация владельца через `Store.configure_role`, а не браузерный маршрут. Проверка создания и сохраненного повтора проходит внутри той же записывающей транзакции `SQLiteOnce.run_guarded`; подготовка счета и pre-checkout также проверяют текущую роль. Уже начатый внешний результат не теряется после отзыва роли: поздний платеж сохраняется для сверки без новой выдачи доступа. Один процесс и локальный диск; несколько рабочих процессов, общий outbox, ограничения частоты, резервные копии, внешние провайдеры, chargeback, мониторинг продакшена и усиление безопасности — отдельные пункты. Памятки демонстрационные, реальные коммерческие материалы должны храниться в защищённом storage проекта. Цифровые товары внутри Telegram не переключаются на внешнюю карточную/крипто оплату.

Приёмка этого примера — установленное приложение, настоящие SQLite/HTTP/процессы, Chrome viewport/theme проверки и покупка во фрейме чужого сайта, как в Telegram Web. Bot transport, launch vectors и native host synthetic; live Telegram/Stars test environment, настоящие клиенты Telegram (Web, Desktop, iOS, Android), физические устройства, screen readers и независимое человеческое удобство не подтверждены. Это experimental example, не объявление production готовности или выпуска 1.0.

Частично сверено 2026-10-05: [Stars digital flow/terms/support](https://core.telegram.org/bots/payments-stars), [createInvoiceLink](https://core.telegram.org/bots/api#createinvoicelink), [SuccessfulPayment](https://core.telegram.org/bots/api#successfulpayment), [Mini App validation](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [openInvoice](https://core.telegram.org/bots/webapps#initializing-mini-apps). Остальные даты API/payment каталога не обновляются. Версия SDK проверяется в consumer; подписанный test vector дополнительно проверяет независимый aiogram parser.

## Возврат Stars и сверка оператором

`refunds.py` связывает магазин с публичными `SQLitePaymentLedger` и `StarsPaymentAdapter`. Сумма возврата берется из сохраненного заказа: только полный целый `XTR`. Тело запроса содержит исходный charge ID и UUID операции; пользователь, сумма, валюта и роль из клиента не принимаются. Прием доверенных платежных сообщений сначала сохраняет небольшой финансовый факт в SQLite, затем обновляет финансовый журнал и представление заказа. Подтверждение оплаты и возврата всегда приходит от серверного SDK или независимо прочитанной истории, не из окна Mini App.

Полномочие оператора отдельно от обычной роли покупателя. Владелец назначает его в доверенной серверной конфигурации через `Store.configure_operator(actor_id, True)`. HTTP-маршрута назначения нет. Заблокированный пользователь не становится оператором даже при сохраненном флаге. Текущая сессия и полномочие повторно проверяются внутри записывающей транзакции финансового журнала при резервировании, начале отправки и повторном запросе.

| Действие | Контракт |
| --- | --- |
| `GET /api/operator/orders/{id}` | Только оператор: заказ, сохраненные charge ID и состояния возвратов |
| `POST /api/operator/orders/{id}/refunds` | Явное решение оператора, JSON `{"operation":"<UUID v4>","charge":"<native charge ID>"}`; те же bearer и точный Origin |
| `GET /api/operator/orders/{id}/refunds/{operation}` | Состояние исходной операции после потерянного ответа; новый возврат не отправляется |
| `POST /api/operator/orders/{id}/refunds/{operation}/reconcile` | JSON `{}`; только чтение аутентифицированной истории и применение найденного доказательства, без повторной отправки возврата |

Ответ `unknown` сохраняет резерв и исходный ID. Даже `True` от SDK в этом примере требует отдельной сверки; повтор того же POST возвращает сохраненное состояние, а новый UUID не обходит резерв полной суммы. Совпадающий исходящий перевод в истории проверяется по получателю, нативному charge ID, исходному payload, полной сумме, направлению и времени. Поиск ограничен пятью страницами по 100 записей. Отсутствующая запись или необязательный payload не доказывают ни успех, ни отсутствие возврата. Тогда состояние остается неизвестным. Операторский аудит сохраняет первоначального автора запроса и фактического автора последующей сверки.

Исходный `shop:<bot_id>:<order_id>` payload сохраняется. Каждый нативный charge получает отдельную финансовую привязку к тому же серверному заказу. Поэтому второй платеж, сохраненный для сверки, тоже можно вернуть; возврат этого второго charge не отзывает право, выданное первым. Подтвержденный возврат исходного выдающего charge закрывает доступ; доверенная запись возврата блокирует прежний доступ уже до применения в финансовом журнале. Поздний платеж в возвращенный заказ сохраняется для сверки и не открывает товар снова. Проверка контента обращается к публичному финансовому журналу, поэтому сбой между финансовым подтверждением и обновлением заказа не оставляет доступ открытым. При следующем запуске незавершенное обновление представления выполняется из сохраненного факта.

Для прежних записей версии схемы 2 нет нативного времени платежа. Миграция сохраняет их существующий доступ по явной политике совместимости; время не восстанавливается из текущих часов или номера строки. Возврат требует повторного доверенного события либо подходящей входящей транзакции SDK с нативным временем. Если такого доказательства нет, ответ `operator-review` сохраняет старые финансовые факты и доступ, а отправка возврата не начинается. После подтвержденного импорта связь с финансовым журналом становится обязательной.

Интерфейс покупателя показывает `refunded` только по своему серверному заказу, убирает доступ к материалу и оплату старого заказа. Терминальный ответ очищает только соответствующий указатель операции. «Продолжить выбор» разрешает собрать новую корзину; новый заказ автоматически не отправляется. Операторский контракт проверяется настоящими HTTP-запросами; отдельный интерфейс назначения полномочий не добавляется.

## Надежный прием polling

`polling.py` подключает публичные middleware aiogram и `SQLiteInbox` к действующему runtime. Вся полученная партия updates сохраняется до возврата SDK и продвижения Telegram offset. При частичной записи и ошибке БД повтор чтения использует тот же offset и уже сохраненные квитанции. Обычная ветка polling не выполняет обработчики второй раз. Два принадлежащих приложению обработчика читают отдельные полосы очереди: обычные updates с priority 0 и pre-checkout с priority 1. Долгое обычное сообщение не занимает обработчик pre-checkout. Неизвестный вид update сохраняется в карантин.

Сетевое чтение `getUpdates` ограничено 25 секундами; десять последовательных ошибок чтения или приема останавливают runtime с ошибкой. SDK-паузы между такими чтениями сохранены. Финансовые RPC проходят через один вызов транспорта и не наследуют этот повтор. Ошибки чтения передаются SDK без исходного текста и цепочки исключений. У обычной очереди пять попыток, срок владения 30 секунд, обработчик ограничен восемью секундами.

`precheckout.py` хранит исходный `received_at`, общий местный срок восемь секунд и состояние ответа. Подтверждение возможно только после фиксации всех квитанций партии и повторной проверки серверных прав. Расчет и native RPC имеют дополнительные границы до двух секунд в пределах оставшегося общего срока. Четыре ожидающих запроса допускаются одновременно; превышение емкости, неполная/неизвестная запись и истекший срок дают карантин без позднего положительного ответа. После аварии до сохранения метаданных неизвестные запросы первой партии с pre-checkout также требуют сверки; промежуточные пустые партии и обычные сообщения не снимают неопределенность. Прежний priority 0 и время старых квитанций не повышаются и не освежаются повтором.

До `AnswerPreCheckoutQuery` фиксируется `reply-started`. Потерянный ответ или авария дают `unknown`; повторная доставка и перезапуск не посылают второй положительный RPC. Даже успешный ответ не делает заказ оплаченным и не открывает материал: нужен подлинный `SuccessfulPayment`. Telegram отсчитывает свои десять секунд с момента отправки запроса; местные восемь секунд от приема не гарантируют этот сквозной срок при задержке доставки, БД или сети. Настоящий цикл SDK с искусственным транспортом проверяет ответ до освобождения заблокированного обычного обработчика; реальная нагрузка Telegram пока не проверена.

Остановка сначала прекращает прием, затем новые задачи и дожидается текущего обработчика; отмена не оставляет работающий SQLite-поток после освобождения OS lock. Не завершенная задача остается для безопасного повтора или карантина. Runtime освобождает свои middleware, FSM и Bot session. Полные updates содержат пользовательские данные: доступ к БД, срок хранения и разбор карантина принадлежат владельцу проекта. Они не передаются в текстовые логи или модель как инструкции. Предел приема — 1 MiB на update; превышение не подтверждает offset и требует решения владельца по емкости/контракту.

Тестовый `offline_refunds.py` использует отдельный файл SQLite как искусственный Stars-сервис. В нем внешний эффект переживает реальную гибель процесса; повтор отправки намеренно не считается идемпотентным. Это позволяет обнаружить второй вызов, но не является платежным sandbox или живой оплатой.

Только контракт возвратов частично сверялся 5 ноября 2026: [refundStarPayment](https://core.telegram.org/bots/api#refundstarpayment), [StarTransaction](https://core.telegram.org/bots/api#startransaction), [TransactionPartnerUser](https://core.telegram.org/bots/api#transactionpartneruser), [RefundedPayment](https://core.telegram.org/bots/api#refundedpayment). Поведение middleware и offset дополнительно проверено в установленном aiogram 3.31.0 и тестом настоящего SDK polling с искусственным транспортом. Остальные даты источников не меняются. Реальные Telegram/Stars, устройства и пилот остаются неподтвержденными.
