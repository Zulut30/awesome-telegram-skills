# Инвентаризация оставшихся требований к production

Дата: 5 ноября 2026. База: `85d266f`, ветка `codex/production-roadmap`. Это сопоставление исходного кода с [планом](../production-plan.md) и [регистром](v1-progress.json), а не приемка. Все 70 pending-пунктов сохранены. Работы других агентов после этой базы не оцениваются; статусы, версии и общий каталог здесь не меняются. Полный verifier и длительные тесты при инвентаризации не запускались.

Обозначения зависимости: **L** — можно реализовать и проверить локально; **TG** — собственные тестовые боты/чаты и Telegram; **D** — реальные устройства; **P** — кабинет/договор/тестовый контур провайдера; **H** — участники исследования; **O** — решение/доступ владельца; **I** — выбранная инфраструктура. Числа — зависимости от исходных пунктов. Наличие файла или теста ниже не означает, что весь пункт выполнен.

## Что не нужно строить заново

- `examples/shop` уже содержит настоящий Python HTTP backend, серверный каталог цен, проверку initData, bearer session, SQLite ledger, ACL заказа/контента и восстановление неизвестного результата создания invoice. Это основа 41–44 и 49, а не только loopback mock. Session rotation/revocation, общая библиотечная модель и полная приемка еще отсутствуют.
- `api-client.ts`, `selection-draft.ts`, `bridge.ts` и `native-api.ts` уже дают строгие request boundaries, abort/timeout, allowlisted user-scoped draft, native capability gates и owned listener cleanup. Они не заменяют прикладной latest-response-wins, безопасную смену аккаунта и operation-specific UI.
- 81–87 и 91–98 имеют существенную инфраструктуру: CI matrix, public API checks, сборку и fresh consumers, recipe execution, security cases, source watchers, MIT, SECURITY/SUPPORT, SBOM/checksums/attestation. Основная работа здесь — закрыть конкретные пробелы и повторно принять итоговые артефакты, а не создавать параллельные механизмы.

## Отдельный риск release candidate

`docs/versioning.md` уже правильно различает Python `1.0.0rc1`, npm `1.0.0-rc.1` и общую identity `1.0.0-rc.1`. Реализация поставки пока ориентирована на одну numeric `X.Y.Z`:

- `scripts/verify_pattern_packages.py` требует numeric version и равенство Python/npm/catalog/examples; имена wheel/tarball тоже выведены из одного значения.
- `scripts/device_report.py::version_tuple` принимает только три числа; его импортирует `scripts/live_acceptance.py`. RC должен оставаться выше порога обязательных отчетов, а не обходить его.
- `.github/workflows/release.yml` и `.github/workflows/publish.yml` валидируют numeric tags; исторические release tags имеют отдельный контракт и не должны переписываться.
- `scripts/build_release.py` строит ожидаемое wheel filename из общей version; нужны разные registry versions при общей source identity и воспроизводимые consumers.

Нужен один узкий release-identity контракт с parsing/comparison/formatting, проверенный на numeric release и RC, затем интеграция в эти существующие механизмы. Не добавлять второй параллельный release pipeline. Report binding должен включать source commit и artifact hashes; не переносить старый passed report на новые байты.

Устройства/провайдеры/исследования/пилоты в исходном дереве не имеют готовых отчетов: `docs/device-checks`, `docs/live-checks`, `docs/internal/usability` и dedicated pilot reports отсутствуют. `device_report.py` проверяет iOS/Android/Desktop/Web и screenshot signatures, но пока не отдельный tablet, provider или usability evidence. `live_acceptance.py` содержит service/group/shop cases и test Bot API probe; он не проверяет сторонние payment providers или долгий production pilot.

## Приоритетные независимые потоки реализации

1. **Durability, 32–40:** guarded actions и inbox можно писать параллельно; после их контрактов — outbox/jobs/notification policy. Изменения должны разделять локальную business exactly-once и внешний unknown result. Затем один интеграционный process-restart набор.
2. **Identity/backend, 41–50:** развивать имеющийся shop, сначала rotation/revoke/role negative cases, затем frontend state/account lifecycle. Не создавать второй backend только ради названия пункта. Этот поток независим от UI tokens и RC tooling.
3. **UI foundation, 51–60:** отдельные exports/CSS tokens и маленькие DOM primitives, затем modal/forms/screens. Сначала заявить стабильный contract, потом browser/axe/focus acceptance и real-device queue. Существующий shell — отправная точка, не готовая design system.
4. **Native workflows, 61–70:** использовать существующие typed catalog/gates; добавлять owned adapters на маленькие группы capabilities, с denied/cancel/late callback tests. Реальные devices можно проверять параллельно готовым flows; не ждать окончания всех adapters для начала измерений.
5. **Payments, 71–80:** сначала общие durable money/receipt/refund/access contracts. Затем независимые optional CryptoPay/Platega/YooKassa adapters с protocol fixtures; настоящие sandbox runs — отдельная очередь после доступа. Четвертый provider зависит от конкретного востребованного сценария.
6. **Release identity, 81/84/85/91/95/98/99:** один worker может устранить numeric-only RC ограничения без пересечения с runtime. Использовать существующие matrix/consumers/SBOM/provenance, а не переписывать CI. Полный verifier запускать после интеграции измененных exports и версии.
7. **External acceptance, 20/67/88–90/93–97/100:** готовить точные задания, manifests и честные report schemas параллельно коду. Фактические passed результаты появятся только после real execution/review; шаблоны и dry runs остаются not-run/blocked, а пункты pending.

Для 81–87 и 91–98 минимальный путь — принять существующую инфраструктуру на итоговом source/artifacts, добавить адресные недостающие проверки и сохранить ограничения. Массовая перестройка этих частей увеличит объем работы без закрытия device/human/provider/pilot требований.
