# Shop: Stars-возвраты и долговечный polling для 0.27

Этот отчет и снимок `source-03` фиксируют итерацию до выделения срочной полосы pre-checkout. Последующее исправление срока, двух обработчиков и неизвестного ответа описано в [отдельном отчете](shop-precheckout-deadline-2026-11-05.md); прежние доказательства не переименовываются.

Это подготовка следующих требований 74/78 и связанных проверок отказов. Версии пакетов, каталог и статусы roadmap этим этапом не принимаются. Локальные SDK-модели и отдельная искусственная платежная БД не являются Telegram sandbox, платежным кабинетом или production-пилотом.

## Хранение и совместимость

`store.py` выполняет аддитивную миграцию схемы магазина 1/2 → 3. Остаются прежние сессии, роли, заказы, receipt/access и исходный `shop:<bot>:<order>` payload. Новые таблицы сохраняют операторское полномочие, неизменяемую связь charge/заказа/покупателя/суммы, доверенный входящий финансовый факт, исходный запрос возврата и аудит действий. Нативное время отсутствующих старых платежей не придумывается.

Для каждого charge создан отдельный `PaymentBinding` того же покупателя, бота и точной суммы: финансовый order ID включает серверный order ID и SHA-256 нативного charge. Это позволяет вернуть второй реальный платеж в состоянии review, сохранив факт его получения. Возврат второго charge не отзывает право, выданное первым. Полный возврат выдающего charge закрывает его товар. Новый charge в уже возвращенный заказ записывается для сверки и не открывает доступ снова.

Старый доступ остается по явной политике совместимости, пока исходный charge не импортирован из доверенного сообщения или входящей записи аутентифицированной истории с подходящим нативным временем. Без такого доказательства запрос возвращает `operator-review` и не отправляет возврат. Подтвержденный импорт включает обязательную проверку публичного финансового журнала при чтении контента.

Доверенный полный факт возврата дополнительно закрывает старый доступ уже при долговечной записи входящего события. Поэтому ни пауза до применения финансового события, ни пришедшее позже исходное подтверждение оплаты не открывают товар. После финансового подтверждения обязательна также независимая проверка `SQLitePaymentLedger.has_access`: тест удаляет из временной БД проекционный факт возврата и все равно получает отказ. Подтвержденные финансовые данные не теряются при сбое обновления представления заказа.

## Полномочия и операция возврата

`refunds.py` использует публичные `SQLitePaymentLedger` и `StarsPaymentAdapter.refund`. Денежный маршрут только `telegram-stars`, целый `XTR`, полный возврат конкретного charge. Сумма и покупатель берутся из серверной привязки. Клиент не задает их, роль или финансовый результат.

Операторское полномочие назначается доверенной конфигурацией через `Store.configure_operator`; публичного маршрута назначения нет. При резервировании, начале отправки и повторе исходной операции callback финансового журнала внутри его записывающей транзакции перечитывает действующую сессию, текущую роль/полномочие и связь с charge. Отзыв между reserve/send блокирует внешний вызов. Отзыв после уже начавшегося эффекта не удаляет его неизвестный результат и аудит.

HTTP предоставляет отдельные защищенные маршруты обзора заказа, явного запроса полного возврата с UUID, чтения исходной операции и сверки. Один и тот же UUID возвращает прежнее состояние без новой отправки; другой UUID не обходит зарезервированную полную сумму. Автор первоначального запроса остается в финансовом журнале. Другой действующий оператор может сверить его по авторитетной истории; аудит отдельно сохраняет фактического автора сверки.

Успешный ответ SDK здесь остается `unknown`, пока не получено независимое доказательство. История сверяется по исходящему направлению, получателю, charge ID, исходному payload, целой сумме и нативному времени; максимум пять страниц по 100 записей. Пропущенный необязательный payload, неправильная сумма, другое направление/лицо и отсутствие записи не подтверждают результат и не разрешают новый POST. Для сохраненного формата payload магазин использует собственное точное сопоставление доверенных SDK-фактов; ожидающий новый формат payload библиотечный mapper не выдается за совместимый со старой схемой.

## Прием до продвижения offset

`polling.py` подключает публичные middleware aiogram 3.31.0 и `SQLiteInbox`. Вся полученная партия updates сохраняется до возврата SDK диспетчеру, который затем продвигает offset. Ошибка записи оставляет прежний offset; уже сохраненная часть при повторе остается дублем, а не новой операцией.

Обычная ветка polling не исполняет обработчики; один принадлежащий приложению worker подает им сохраненные claims. Неизвестный вид update остается в карантине. Обработчик, который отсутствует или исчерпал пять попыток, не становится успешной обработкой молча. Ошибка после приема финансового сообщения повторяется из очереди и сохраненного финансового факта с защитой от повторной выдачи.

Сетевое чтение `getUpdates` ограничено 25 секундами, десять последовательных ошибок чтения/приема завершают runtime с ошибкой. Каждая локальная SQLite-операция имеет свой конечный timeout; offset при неполной партии не подтверждается. Финансовые RPC вызывают транспорт один раз и не наследуют чтение с повтором. Ошибка чтения передается циклу SDK как статическое `PollingReadFailure` без исходного текста и цепочки, чтобы ошибка разбора ответа не вывела пользовательские данные в лог SDK. Обработка очереди ограничена восемью секундами, lease — 30; расчет pre-checkout и ответ отдельно ограничены тремя секундами каждый. Реальные сроки под нагрузкой без настоящего бота не заявляются.

При остановке прекращается прием и выдача новых claims, затем завершается или отменяется текущий обработчик. Отмена дожидается принадлежащего приложению SQLite-потока и сохраняет задачу для безопасного повтора. SDK-middleware, worker, FSM, Bot session и OS lock освобождаются в порядке владения. Payload очереди — данные, не инструкции ИИ; полный update не выводится в журналы. Права на файл, retention и разбор карантина принадлежат владельцу.
