# Shop: отдельная обработка pre-checkout и неизвестного ответа

Продолжение подготовки 0.27 после [проверки возвратов](shop-stars-refunds-2026-11-05.md). Снимок `shop-refunds/source-03` с 45 Python, 5 Node и 262 Chrome остается свидетельством предыдущей итерации. Он не доказывает исправление срока pre-checkout.

## Изменение

В `polling.py` теперь два конечных обработчика, без отдельной задачи на каждый update: обычная полоса `priority=0` и срочная `priority=1`. После получения партии настоящий SDK middleware сохраняет все квитанции, затем одним commit переводит метаданные pre-checkout в `ready`, затем возвращает результат SDK для продвижения offset. Обработчик срочной полосы не проходит обычный dispatcher повторно. Обработчик обычной полосы не разрешает устаревший pre-checkout с priority 0.

`precheckout.py` хранит первоначальное время, срок, native query ID, update ID и хеш полей финансового запроса. Исходное время совпадает с `InboxRecord.received_at`; повтор не дает новый срок. Общий местный бюджет — восемь секунд, дополнительный расчет/ответ ограничены двумя секундами каждый внутри оставшегося бюджета. Положительный ответ проверяет роль и заказ еще раз в writer-транзакции перед сохранением `reply-started`; перед сетевым вызовом проверяется оставшийся срок. Неполная партия, сбой записи, неизвестное первоначальное получение, истечение срока и превышение четырех мест дают отказ от подтверждения/карантин. Никакое время не сдвигается ради сортировки.

До отправки любого ответа сохраняется `reply-started`. Потеря ответа, отмена или авария сохраняют неизвестный исход, который не вызывает повторный положительный RPC. Авария до сохранения самой партии обнаруживается предварительным признаком владельца: неизвестные запросы первой полученной после такого перезапуска партии с pre-checkout требуют сверки. Промежуточные пустые партии и обычные сообщения не снимают неопределенность перезапуска или неполного приема; исходный неизвестный срок не заменяется свежим разрешением. Успешное подтверждение pre-checkout не создает платежную квитанцию и доступ; они появляются только после доверенного `SuccessfulPayment`.

Telegram требует ответа в десять секунд **с момента отправки запроса Telegram**. Местный срок от приема не доказывает выполнение этого срока при внешней задержке доставки, высокой нагрузке, блокировке диска или сбое сети. Переполнение сохраняется в карантине, а не в бесконечной очереди фоновых задач. Тестовый транспорт не заменяет настоящего Telegram-бота и платежный кабинет.

## Совместимость общей очереди

`SQLiteInbox` переходит со схемы 1 на 2 в одной SQLite-транзакции. Добавляется `priority INTEGER NOT NULL DEFAULT 0`; прежние payload, `received_at`, доступность, lease, попытки и бизнес-таблицы сохраняются. Отказ записи версии откатывает и `ALTER TABLE`. Неизвестная версия отклоняется. Это схема общей очереди; схема магазина остается 3, финансового журнала — 2.

`receive(priority=0)` принимает точный `int` 0–255. Дубль сохраняет первоначальный priority и время. `InboxReceipt` и `InboxRecord` показывают сохраненный priority. `claim(priorities=None)` сохраняет прежний FIFO по всем полосам; явный фильтр — tuple из 1–16 различных точных int 0–255, SQL-параметры, без изменения порядка. Пустой tuple, list, bool и повторы отклоняются. Старые записи pre-checkout в полосе 0 не получают новую свежесть.

## Проверки

В `test_precheckout.py` добавлены восемь случаев:

| Сценарий | Наблюдение |
| --- | --- |
| Настоящий `Dispatcher.start_polling`, обычный обработчик закрыт `AsyncEvent` | Положительный `AnswerPreCheckoutQuery` приходит до открытия события, внутри местного бюджета; заказ остается awaiting, доступа нет |
| Истечение реально прошедшего времени и перезапуск | Ни одного положительного RPC, исходное время сохранено |
| Ошибка второй записи партии | Нет ready/положительного RPC; повтор использует тот же offset и первоначальное время |
| Емкость 1 и два запроса | Второй сохранен в карантине, позднего подтверждения нет |
| Потерян ответ положительного RPC | unknown; повтор и открытие SQLite после перезапуска оставляют количество True равным 1 |
| Старый priority 0 или квитанция без метаданных первого приема | Нет повышения приоритета или обновления срока, только карантин |
| Реальный `os._exit(88)` до записи метаданных | Настоящий SDK polling после перезапуска получает пустую партию, обычное сообщение и затем query; offsets `[None, None, 1260, 1261]`, положительного RPC нет |
| Реальный `os._exit(89)` после внешнего положительного эффекта | Отдельный fsync-файл сохраняет один эффект; журнал при открытии unknown, повтор не вызывает True и не выдает доступ |

В `test_inbox.py` 24 случая включают прежние проверки и пять новых: полосы/default FIFO, неизменность дублей, проверку типов, реальное открытие БД версии 1 и откат неудачной миграции. Полная приемка магазина требует минимум 53 Python и все восемь имен новых сценариев, плюс прежние пять Node и 262 Chrome. Логи первого полного прогона находятся в `output/production-run-2026-11-05/shop-precheckout/source-01/`. Последние проверки неизвестного приема и сохранения неопределенности через промежуточные партии повторены вместе со всеми 53 Python и 24 Inbox в `source-03/`; там сохраняются финальные команды и SHA-256. Неизменные UI/fixture проверены 262 случаями настоящего Chrome в `source-01/browser/`, а не объявлены новым прогоном Chrome в `source-03`. Промежуточный `source-02` сохранен отдельно. Установка финальных wheel/tarball в отдельный consumer и формальная приемка принадлежат центральному прогону; live-подтверждение отсутствует.
