# Stars: платеж, возврат и оплаченный доступ

Термины: **неизвестный результат** — запрос мог выполниться, но ответа нет (таймаут, обрыв связи); повторять вслепую нельзя, сначала сверка; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

`StarsPaymentAdapter` из `telegram_patterns.aiogram` связывает существующий `Bot`
и `SQLitePaymentLedger`. Он сохраняет целую сумму XTR, перепроверяет текущие права
оператора перед возвратом и сопоставляет подтвержденный возврат с конкретным
списанием. Новый бот, HTTP-клиент или SDK не создается. Сессию закрывает приложение.

Цифровые товары и услуги внутри Telegram оплачиваются Stars. Наличие внешнего
платежного адаптера не меняет это правило. Для физического товара или услуги
нужно отдельно выбрать разрешенный маршрут и проверить договор магазина.

## Граница доверия

`Message`, `SuccessfulPayment` и `RefundedPayment` можно сконструировать вручную.
SDK-тип не удостоверяет происхождение события. `paid_event()` и `refund_event()`
разрешено вызывать только серверному обработчику после проверенного входа Telegram:
одного принадлежащего приложению polling-процесса либо аутентифицированного webhook,
сохраненного до подтверждения приема. Клиент Mini App не передает этим методам
«подтверждение оплаты». Для повторной обработки сохраняйте сам update и серверную
связь с заказом; не полагайтесь только на результат предыдущего обработчика.

Адаптер поддерживает личный чат покупателя: проверяются бот, `chat.id`, человек в
`from_user`, отсутствие Business-контекста, исходная операция счета, payload,
целая сумма и XTR. Поддержку групповых счетов или иных источников сервисных
сообщений этот узкий маршрут не обещает без отдельной проверки реального клиента.

`invoice_payload(binding, invoice_operation_id)` — SHA-256 полной серверной
привязки и ID операции, а не секрет или разрешение. Сохраните заказ и намерение
до отправки счета; передайте этот payload существующему `stars_invoice(...)`.
Не рассчитывайте цену по браузерным данным.

## От счета до выдачи

`paid_event(binding, message, invoice_operation_id=..., evidence_ref=...)` —
асинхронный разбор доверенного `successful_payment`. Локальное чтение исходной
операции завершается вне event loop. Событие содержит нативный charge ID, точную
сумму, `Message.date` и, для подписки, `subscription_expiration_date`. Срок не
вычисляется из текущего времени или даты наблюдения. Разовый платеж не может
незаметно стать подпиской; подписка требует нативного признака повторного платежа
и положительного оплаченного периода.

Передайте результат журналу через закрытый серверный `PaymentVerifier`. Сам
`ProviderEvent` остается обычной структурой данных: публичный endpoint не должен
принимать ее как доказательство. Подтверждение оплаты, доступ и аудит фиксируются
одной транзакцией. Повтор одного списания не выдает товар еще раз.

Pre-checkout — отдельное согласие принять платеж, без выдачи доступа. Telegram
должен получить ответ в течение 10 секунд с момента отправки запроса. Проверяйте
текущий заказ быстро; если проверка недоступна, отвечайте отказом. В локальном
примере проверка и `answerPreCheckoutQuery` помещены в бюджет 3 секунды. Такой
бюджет не доказывает время сетевой доставки Telegram.

## Возврат и неизвестный исход

```python
from telegram_patterns.aiogram import StarsPaymentAdapter

adapter = StarsPaymentAdapter(bot, ledger, timeout_seconds=15)
operation = await adapter.refund(
    binding, charge_id, "refund:1", operator_id,
    check=current_operator_acl,
)
```

`refund()` принимает только целый полный XTR-возврат. До сети журнал резервирует
полную сумму конкретного подтвержденного списания. В той же writer-транзакции
`check(connection, operation, replayed)` проверяет текущие роль и объектные права
при резервировании, повторе и запуске. Затем единственный `PaymentClaim`
разрешает один `Bot.refund_star_payment(user_id=..., telegram_payment_charge_id=...)`
вне транзакции. Журнал уже содержит полную привязку, charge, сумму, автора и ID
операции — все аргументы этого нативного вызова. Middleware сессии не должно
автоматически повторять записи.

`timeout_seconds` — целое 1…20 секунд; срок владения отправкой на 5 секунд больше.
Отмена ожидания не отменяет удаленный возврат. Ошибка, таймаут, отказ ответа и даже
нативный `True` оставляют операцию требующей независимой финансовой сверки.
Адаптер не отзывает доступ по клиентскому callback, локальному boolean или
скриншоту. Если подтвержденное сервисное событие уже пришло одновременно с
ответом API, возвращается фактическое сохраненное состояние.

Падение процесса может оставить `sending`. После истечения владения вызовите
`ledger.recover_expired(binding)`; состояние станет `unknown`, резерв сохранится.
Новый ID возврата не обходит занятый остаток. `refund()` для начатой операции не
выдает второе разрешение на отправку.

## Подтверждение возврата

Доступны два серверных пути:

- `refund_event(binding, message, invoice_operation_id=..., evidence_ref=...,
  operation_id=...)` разбирает доверенный `RefundedPayment`. При отсутствии
  локального намерения допустим `operation_id=None`: реальный внешний возврат
  все равно должен отозвать право данного списания.
- `reconcile_refund(binding, operation_id, operator_id,
  invoice_operation_id=..., check=...)` читает `getStarTransactions` через тот же
  аутентифицированный `Bot`. Это только чтение; повторной отправки нет.

Сверка проверяет текущие права оператора еще раз. По умолчанию она читает не более
5 страниц по 100 операций; допустимы 1…20 страниц и 1…100 строк. У каждого GET
тот же ограниченный срок ожидания. Нативная операция должна иметь исходящий
`receiver` без `source`, тип `invoice_payment`, нужного покупателя, исходный charge
ID, точный payload и полную положительную целую сумму без нанодолей. Нативная дата
не может быть раньше сохраненной оплаты или позже времени сверки.

Bot API использует **положительную величину** суммы и определяет направление
через `source`/`receiver`; отрицательная сумма не принимается как возврат. ID
возврата совпадает с ID исходной операции. Эти детали сверены с официальным
сериализатором Telegram Bot API, а не выведены из названий полей.

`invoice_payload` у `TransactionPartnerUser` формально необязателен. Если он
отсутствует или найденная страница неполна, автоматическая сверка оставляет
`unknown`. Отсутствие совпадения не доказывает отсутствие возврата: нужны позднее
доверенное событие либо операторская сверка. Нельзя превращать пустой поиск в
разрешение отправить `refundStarPayment` заново.

Подтвержденное наблюдение и ожидаемая ревизия передаются в
`ledger.reconcile_operation(...)`. Изменившееся состояние нельзя перезаписать
устаревшим ответом. Один и тот же нативный возврат, увиденный и в update, и в
истории, не уменьшает остаток дважды. Полный возврат отзывает только связанный
charge; другой невозвращенный оплаченный период остается действительным.

## Проверка и оставшиеся границы

`examples/api-reference/python/bot_stars_payments.py` выполняет полный локальный
сценарий через настоящий aiogram Dispatcher и `StubSession`: invoice,
pre-checkout, повтор `successful_payment`, сохраненный charge, возврат,
независимый GET и отзыв доступа. Это путь внутри репозитория, а не команда
запуска из произвольного каталога установленного wheel.

Тесты используют настоящую файловую SQLite, отдельную БД подставного Telegram,
конкурирующие процессы и аварийный выход после внешнего эффекта. Они не доказывают
работу тестового бота, настоящие списание/возврат Stars, сроки доставки Telegram
или формат сервисного сообщения на физических клиентах. Эти проверки остаются
отдельной живой приемкой. Отмена автопродления через `editUserStarSubscription`
и прием `BotSubscriptionUpdated` в этот адаптер возврата не входят; чистая модель
периодов в журнале не заменяет такую прикладную интеграцию.
