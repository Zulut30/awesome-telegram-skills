# Запуск, наблюдение и восстановление

Это эксплуатационный runbook для Python-бота/backend и TypeScript Mini App.
Он дает варианты для уже доступной инфраструктуры; новый hosting, контейнерный
оркестратор, secret manager или сервис мониторинга не обязателен. Предоставленные
локальные пакеты пока не следует искать в PyPI/npm. Начните с
[подключения библиотеки](for-agents.md) и [README магазина](../examples/shop/README.md).

## Профиль запуска и ответственность владельца

| Уже доступная среда | Запуск | Что проверить перед переключением |
| --- | --- | --- |
| Windows/Linux/macOS с постоянным процессом и локальной SQLite | Отдельное окружение Python, один процесс polling на bot ID, постоянный каталог данных; текущий supervisor/планировщик владельца | Кто запускает и останавливает процесс, учетная запись, права каталогов, сохранность диска, журнал и отсутствие второго consumer |
| Существующий HTTPS reverse proxy для Mini App | Тот же Python backend на loopback и собранный TypeScript frontend; proxy публикует точный origin | TLS, прямой frontend route, правильный origin, body/time limits, постоянный путь SQLite вне каталога release |
| Существующий HTTP/webhook host | Совместимый webhook adapter проекта, проверка secret header и durable прием до HTTP ACK | Совместимость процесса/storage, повторы, fencing старого consumer; пример магазина сам запускает polling и не становится webhook приложением от смены URL |

SQLite здесь предполагает постоянный локальный диск и согласованное владение
одним процессом. Ephemeral/serverless filesystem или сетевой том нельзя объявить
подходящим без отдельной проверки контракта storage. Уже используемый PostgreSQL,
SDK, frontend framework и инфраструктуру сохраняйте. Профили — варианты, а не
утверждение, что для пользователя уже выбран или проверен production host.

Перед релизом зафиксируйте в закрытой конфигурации владельца: идентификатор release,
SHA-256 обоих библиотечных архивов и application wheel, версии Python/SDK/Node,
команду и cwd процесса, DB path, origin, bot ID без токена, владельца остановки,
путь журналов, предыдущий release и его правила совместимости. Сборки и venv
держите отдельно от данных; не обновляйте работающий venv на месте. Для frontend
используйте его lockfile, предоставленный tarball и проверенную build-команду из
README приложения. `SKILL.md` не устанавливает runtime-зависимости.

## Секреты и конфигурация

Передавайте `BOT_TOKEN` и необходимые проекту секреты через уже имеющуюся
защищенную настройку процесса. Не помещайте значения в argv, Git, frontend bundle,
URL, скриншоты или отчет проверки. Не выводите `env`, конфигурацию целиком или
полный `BotSettings`. `.env` допустим, только если приложение его действительно
загружает и владелец ограничил доступ; магазин читает окружение, наличие `.env`
само по себе его не настраивает.

Разделяйте test и production token, базы и платежный режим. Проверяйте наличие
нужных имен без печати значений. На Windows используйте ACL учетной записи сервиса
для секретов, данных, копий и родителей каталогов; на POSIX ограничьте чтение
секретов владельцем и запись каталогов (например, 0700). Не применяйте массовое
изменение прав к чужим каталогам. Backup содержит персональные и финансовые
данные и требует того же ограничения доступа. Ротация токена требует обновления
процесса и проверки redaction; не переносите старые sessions в новый trust context.

## Запуск и остановка

Конкретная команда магазина приведена в его README: `telegram-shop-example`
требует `--database`, `--frontend`, `--origin`, `--terms`, `--terms-version`,
`--support` и при необходимости `--port`. Используйте реальные условия и контакт
своего проекта. Для backend Mini App нужен точный HTTPS origin; loopback HTTP
разрешен только explicit offline fixture. Проверенный локальный witness ниже
запускает fixture и не вызывает live entrypoint с синтетическим токеном.

1. До первого запуска сохраните manifest release и текущую конфигурацию.
   Проверьте catalog/API установленных версий. Убедитесь, что нет другого polling
   consumer и установленного webhook; не очищайте pending updates ради запуска.
2. Проверьте доступ к постоянным каталогам под учетной записью сервиса, место на
   диске, корректность origin и сборки frontend. Миграции выполняйте по контракту
   конкретной версии. Для магазина текущий schema 3 не означает совместимость
   любого будущего или прошлого release.
3. Запустите одну команду через выбранный владельцем supervisor либо вручную
   для тестовой среды. Сохраните PID/process identity и release ID; один номер PID
   без подтверждения принадлежности не разрешает остановку чужого процесса.
4. Проверьте процесс и HTTP readiness, затем один допустимый пользовательский
   сценарий. Для настоящего Telegram это отдельная live проверка; локальный
   probe не доказывает доставку updates, платеж или физический WebView.
5. Для остановки используйте штатный graceful stop выбранного supervisor/процесса,
   дождитесь закрытия HTTP, соединений, in-flight writes и освобождения lock.
   Не запускайте replacement, пока старые writers не завершены. Не удаляйте
   lock-файл для обхода живого владельца. Force kill требует разбора незавершенных
   операций и их прежних ID; успешная отправка могла предшествовать аварии.

## Monitoring без нового сервиса

Достаточны текущий supervisor, локальные структурированные логи и периодическая
проверка владельцем. Масштабируйте сбор по потребности. У магазина
`GET /api/readiness` дает 200/`ready:true` либо maintenance 503/`ready:false`;
недоступный порт, timeout, не-JSON и неожиданный статус считаются отказом probe.
Он проверяет operational gate, а не весь путь пользователя или состояние всех
очередей. Он не заменяет liveness процесса, память/диск и успешность приема updates.

| Наблюдение | Действие |
| --- | --- |
| Процесс отсутствует, HTTP недоступен или readiness false | Остановить переключение, проверить release/config/storage и журнал; marker не снимать |
| Растут ошибки, задержка или возраст/размер backlog | Проверить зависимость и capacity, удержать исходящие повторы до классификации результата |
| `unknown`, потерянный ответ, повторы updates | Сохранить scope, operation ID, attempts и revision; сверять фактический эффект, не создавать новый ID |
| Backup просрочен, места мало, проверка копии не прошла | Исправить хранение и выполнить новый backup в новый файл; непроверенный снимок не использовать |
| Неизвестная schema/модель прав после смены release | Оставить сервис закрытым до совместимой миграции или исправленного release |

Пишите время, release, безопасный correlation/operation reference, фиксированный
код ошибки и агрегированные counters. Не логируйте payload, initData, bearer,
токены, полные URL Bot API или сведения оплаты. Логи ограничивайте по размеру и
сроку. Интервал probes, допустимую задержку, возраст backup и контакт реагирования
задает владелец по своим RPO/RTO и нагрузке; универсальный SLA здесь не обещается.
Эти counters не объявляются новыми endpoint магазина.

## Backup и restore

Используйте [sqlite-recovery](sqlite-recovery.md): защищенные существующие roots,
новое имя snapshot, SQLite backup API вместо копирования занятого `.sqlite`.
Настоящие CLI-команды, проверяемые helper в собственной test-среде:

```powershell
& $consumerPython -I -m telegram_patterns backup-sqlite live.sqlite checkpoint-001.sqlite --source-root $dataRoot --target-root $backupRoot --json
& $consumerPython -I -m telegram_patterns restore-sqlite-new checkpoint-001.sqlite inspect-only-001.sqlite --source-root $backupRoot --target-root $recoveryRoot --json
```

Переменные содержат пути владельца; это не готовые production значения. В test
helper все они создаются заново. Общий restore создает файл для проверки данных;
**сырой restored-файл не запускайте и не копируйте поверх рабочего пути**.
Для магазина используйте [prepare и inspect](shop-recovery.md). Остановите всех
writers до prepare; его OS locks не останавливают произвольный SQLite-клиент.
Snapshot SHA-256 сверяйте с независимо сохраненным manifest, не с данными
недоверенного запроса. Candidate публикуется уже в maintenance и остается там.

Проверьте exit code, SHA-256, `directory_synced` и `cleanup_complete`. На Windows
`directory_synced=false` не доказывает долговечность при потере питания. При
`publication-unknown` сначала осмотрите существующую цель без перезаписи. Не
удаляйте ее ради retry. Храните несколько проверенных поколений; копия только на
том же диске не защищает от потери диска. Расписание, отдельное доступное место
хранения, срок и защита копий принадлежат владельцу и не требуют конкретного облака.
Периодически восстанавливайте выбранный snapshot в новый закрытый путь и
проверяйте бизнес-инварианты. Размер/хеш сами по себе не доказывают восстановимость.

Восстановленные sessions отзываются; роли/операторские права и платный доступ
требуют свежего доверенного подтверждения. Pending из checkpoint мог уже вызвать
эффект после снимка. Telegram acknowledgement и внешние оплаты файлом не
откатываются. Не очищайте unknown, IDs или ревизии. `inspect` с exit 3 ожидаем
для подготовленного candidate; это не разрешение на activation. Команд
activate/unpause и JSON платежного доказательства здесь нет.

## Откат кода отдельно от данных

При дефекте нового release сначала остановите его и всех writers. Сохраните
нынешнюю БД, ее журнал и manifest. Откат кода означает возврат **предыдущего
неизменяемого артефакта и его команды/конфигурации при текущем файле данных**.
Восстановление старого snapshot — другая процедура, она может потерять локальные
изменения и не отменяет внешние эффекты.

До возврата старой команды подтвердите на отдельной копии текущего состояния,
что предыдущая версия читает текущие schema/ledger/IDs/права и не повторяет эффекты.
Учитывайте все компоненты, а не только номер `shop_schema`. Неизвестная
совместимость, активный writer или любой recovery marker закрывают запуск.
Недостаточны одинаковый импорт, `ready:true` или совпадение SQL schema: семантика
старого кода также должна быть совместима. Без такого доказательства оставьте
maintenance и подготовьте совместимый исправленный release; не понижайте schema
вручную. Даже прежний магазин без recovery guard не должен получать candidate.

После разрешенного возврата команды проверьте process, readiness и сценарий,
сохранив прежние operation IDs и unknown. Наблюдайте ошибки/backlog; не запускайте
оба release одновременно. Локальный helper проверяет stop/restart прежней команды
**на том же установленном артефакте**, а также отказы writer/marker/schema.
Он не доказывает совместимость двух разных версий приложения, которой нельзя
обещать для произвольной будущей миграции.

## Исполняемая локальная проверка

Нужен отдельный consumer с предоставленными библиотечным wheel 0.28.0 и
application wheel магазина 0.1.0 вместе с его совместимыми зависимостями.
Установка описана в README магазина; можно использовать consumer, уже созданный
`verify_shop_example.py`. Helper не устанавливает зависимости и не загружает .env.

```powershell
python scripts/check_local_operations.py --python 'C:/owned-consumer/environment/Scripts/python.exe' --output output/local-operations-check
```

```bash
python3 scripts/check_local_operations.py --python /owned-consumer/environment/bin/python --output output/local-operations-check
```

Output должен отсутствовать. Helper запускает isolated Python `-I` за пределами
checkout, подтверждает installed origins, создает только собственные temporary
SQLite/HTTP fixture и synthetic token; рабочие пути/токены аргументами не принимает.
Он реально запускает loopback HTTP, опрашивает readiness, gracefully останавливает
процесс, делает backup/restore/prepare/inspect через CLI, проверяет сохранение
unknown и отказы перезаписи, active writer, marker и schema, повторяет прежнюю
команду и видит отказ probe после остановки. Raw restored-файл никогда не запускается.
SDK fixture запрещает внешнюю сеть; это контроль тестового кода, не OS sandbox.

`report.json` содержит стадии, версии, хеши import modules, probe latency и признаки
синхронизации. Он не содержит токенов или пользовательских данных. Exit 0 означает
успех локального witness; exit 2 — отказ/ошибку. После отказа output сохраняется,
повтор требует нового имени. Производственные ACL/secret injection, TLS, выбранный
host, потери питания и live Telegram/provider проверяются только в своей реальной
среде и этим report не подтверждаются.

Сценарии для проверки решений агента из [evaluation](evaluation.md): существующий
Python stack остается; узкий запуск не добавляет обязательный сервис; восстановление
не повторяет неизвестную запись; зеленый readiness не принимается за пользовательский
путь. Авторский разбор runbook и выполнение helper не заменяют независимую оценку
решения агента или исследование с участниками.

Источники исполняемых контрактов: текущие локальные
[runtime](../examples/shop/src/telegram_shop_example/runtime.py),
[offline fixture](../examples/shop/src/telegram_shop_example/offline.py),
[recovery](../examples/shop/src/telegram_shop_example/recovery.py) и
[sqlite-recovery](sqlite-recovery.md). Новые version-specific контракты внешнего
провайдера этим runbook не вводятся и даты их прежней сверки не обновляются.
