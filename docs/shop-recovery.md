# Подготовка восстановленного магазина

Термины: **outbox** — события, сохраненные в той же транзакции, что и изменение данных; отдельный обработчик выполняет их позже.

Этот маршрут создает **новую закрытую копию** магазина. Он не активирует ее,
не переключает работающий процесс и не подтверждает отсутствие внешних эффектов
после checkpoint. Исходная БД и snapshot сохраняются.

Восстановление может вернуть отозванные после снимка sessions, роли, operator
capabilities и доступ. Сохраненный pending мог уже привести к отправке;
подтверждения updates на стороне Telegram файлом не откатываются.

## Подготовка offline-копии

Остановите всех писателей: процесс магазина, polling/webhook consumers, таймеры,
очереди и другие приложения с этим файлом. Используйте проверенный snapshot и
существующие каталоги с правами владельца сервиса. CLI не назначает Windows ACL,
не добавляет хостинг, cloud storage или шифрование.

```powershell
python -m telegram_shop_example.recovery prepare --live C:/shop/data/live.sqlite --snapshot C:/shop/backups/checkpoint.sqlite --candidate C:/shop/recovery/candidate-new.sqlite --live-root C:/shop/data --snapshot-root C:/shop/backups --target-root C:/shop/recovery --bot-id 100 --expected-snapshot-sha256 <64-hex-sha256>
python -m telegram_shop_example.recovery inspect --candidate C:/shop/recovery/candidate-new.sqlite --target-root C:/shop/recovery
```

Замените пути, bot ID и SHA-256 собственным проверенным контекстом. Команды не
требуют токена бота и не принимают JSON в качестве платежного доказательства.

`prepare` принимает только отсутствующий final candidate. Оба настоящих
`ProcessLock` — старой БД и нового пути — берутся до восстановления. Активный
владелец дает отказ; lock координирует только соблюдающие его приложения и
не заменяет остановку остальных writers.

1. Проверить roots, snapshot SHA и shop schema 3. Если используется общий
   `SQLiteOutbox`, проверить schema 1; обычному магазину эта очередь не требуется.
2. Через `restore_sqlite_new` создать копию в закрытом временном каталоге.
3. Одной транзакцией добавить recovery marker и audit, удалить все restored
   sessions, выставить blocked известным акторам и отключить operators.
4. Pending/sending outbox перевести в unknown: прежние scope, operation keys,
   payload и attempts сохраняются; revision увеличивается на один. Это fence,
   а не новая отправка. Уже unknown не очищаются.
5. Проверить SQLite и опубликовать новый файл. До quarantine commit final path
   отсутствует; после публикации он уже содержит обязательный guard. Crash до
   commit оставляет private stage, после публикации — закрытую копию.

Paid/access facts не переиздаются и не признаются свежим разрешением на доступ.
Неизвестные файлы временного каталога сохраняются, рекурсивной очистки нет.
`cleanup_complete=false` требует разбора остатка владельцем, а не удаления цели.

Результат содержит отдельные SHA-256 snapshot и подготовленного candidate.
На Windows `directory_synced=false` не обещает сохранность записи каталога при
потере питания. `--deadline-seconds` ограничивает проверяемую работу SQLite/hash,
но не прерывает зависший системный вызов или `fsync`.

## Поведение закрытой копии

`shop_recovery_meta` — отдельная schema 1. Само наличие recovery marker, в том
числе неизвестного или неполного, закрывает приложение. Строка `ready` или флаг
запуска не открывают этот gate.

- `Store` в maintenance не выполняет миграции или recovery. Все SQL-пути закрыты,
  включая fresh actor/session, роли и operator configuration.
- HTTP возвращает 503 `recovery-maintenance`. `GET /api/readiness` возвращает
  503 с `ready:false` и режимом maintenance.
- Runtime поднимает только закрытый HTTP/readiness. Polling, обработчики,
  финансовый recovery и workers не запускаются.
- SDK transport приложения и официальный payment router проверяют тот же gate;
  прямое подключение router не возобновляет ответы или платежные вызовы.

Обычная БД без marker сохраняет прежний режим. Произвольную администраторскую
копию старого файла поверх рабочего пути нельзя надежно распознать без внешнего
свидетеля. **Восстановление поверх рабочего пути и запуск сырой restored-копии
запрещены процедурой.** Используйте новый подготовленный candidate; старый путь
сохраняйте для разбора.

## Exit codes

| Код | Значение |
| --- | --- |
| 0 у prepare | Новый candidate подготовлен, но `ready:false`; активации нет |
| 0 у inspect | Обычная БД имеет открытый operational gate |
| 3 у inspect | Maintenance/непроверенное состояние; private access и workers закрыты |
| 2 | Отказ аргументов, schema/context/hash/path/owner или подготовки |
| 4 | Публикация могла завершиться: сначала inspect, без перезаписи цели |

Ошибки фиксированы: токены, исходные пути и текст SQLite не печатаются. Повтор
prepare поверх существующей цели отклоняется; для осмотра используйте inspect.

## Что остается до активации

Команд activate/unpause нет. Нельзя включить приложение произвольным JSON,
очисткой unknown или новым operation ID. Отдельный доверенный процесс должен
сверить текущие права, sessions/deployment epoch, финансовые и другие эффекты
после checkpoint, отсутствующие подтвержденные updates и все исходящие очереди.
Недоступная история, прошедшее время и пустой ответ не разрешают повтор.

Проверка активации, инфраструктуры и внешних платежных/Telegram сред остается
отдельной работой. Закрытый маршрут не означает выполнение всего пункта 96
или готовность к production.
