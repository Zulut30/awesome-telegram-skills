# Безопасные повторы и проверка итога

Термины: **CAS** — сравнение с заменой: запись сохраняется, только если версия не изменилась с момента чтения; квитанция (receipt) — сохраненная запись о выполненной операции; повтор возвращает ее вместо второго эффекта; **outbox** — события, сохраненные в той же транзакции, что и изменение данных; отдельный обработчик выполняет их позже; **сверка** — запрос фактического состояния у провайдера или в хранилище перед повтором или выдачей.

Повтор — новое выполнение эффекта. Он безопасен только по контракту конкретной операции. Библиотека не повторяет денежную операцию, выдачу доступа или отправку сообщения на основании одного текста exception.

## Решение после ошибки

| Операция и наблюдение | Действие host |
| --- | --- |
| Чтение: timeout, transport failure, временный отказ | Bounded retry с backoff; старый ответ не перезаписывает новый запрос. Закончился общий deadline/бюджет — остановиться. |
| Локальная идемпотентная SQLite запись | Повторить **тот же** server-owned scope, operation ID и payload через ledger; заново проверить текущий ACL. Другой payload — конфликт, новый ID не решает конфликт. |
| Remote write с настоящим provider idempotency key | Сначала сверить статус по устойчивому ID; сохранять тот же key, payload и merchant context. Проверить срок хранения key и протокол провайдера. Условие `GET не нашел` само по себе не исключает поздний эффект прежнего запроса. |
| Подтвержденный временный отказ **без эффекта**, включая валидный flood rejection | Сохранить retry time и attempts; ждать не меньше `retry_after`, затем повторно проверить consent, ACL, deadline и лимит попыток. |
| Write: потерянный ответ, timeout после отправки, worker crash в состоянии sending, неразобранный ответ | Сохранить `unknown`; не отправлять автоматически повторно. Сверить provider/operation status либо передать оператору. |
| Постоянный отказ, отписка, недоступный получатель, истекший deadline | Терминальное состояние; не продолжать бесконечную очередь. Повторный opt-in не оживляет завершенные задания сам по себе. |

`safe_error_report(error, operation='write')` консервативно возвращает `outcome='unknown'` и `recovery='reconcile'` для необъясненной remote ошибки. `ValidationFailure`/`PermissionDenied` означают известный pre-effect отказ только там, где host действительно установил этот факт. Не превращайте arbitrary HTTP exception в `ValidationFailure`, чтобы получить удобный retry. `operation='read'` не подходит для create/refund/capture/выдачи доступа.

## Backoff и бюджет

Храните attempts, next_attempt_at и общий deadline в durable storage. Пример политики проекта: не больше пяти попыток; задержка `min(30, 0.5 * 2**(attempt-1))` секунд плюс ограниченный jitter. Это пример настройки, не гарантия SLA Telegram. Проверенное `retry_after` задает нижнюю границу ожидания; не обрезайте его вниз ради локального cap. Если сервер просит ждать дольше допустимого deadline, завершите/отложите задание для оператора. Значение retry_after проверяется как конечное неотрицательное число; некорректный ответ не дает разрешения на мгновенный повтор.

Общий и per-recipient rate limit координируют все workers в shared storage. Сон одного процесса не ограничивает другой. После рестарта сохраняются число попыток, cooldown, состояние и отсутствие согласия на отправку. Отмена локального await не доказывает отмену удаленного эффекта.

## Сверка опасного эффекта

1. До первого вызова сохранить устойчивый ID операции, проверенные сервером автора и контекст, исходные данные и их хеш и состояние намерения вместе с бизнес-изменением.
2. До remote call атомарно перейти в sending и сохранить attempt/claim token. После успешного ответа сохранить проверенный receipt/charge/message ID.
3. Потеря ответа или истекший sending lease переводят в unknown. Новый worker получает право **на сверку**, а не на отправку.
4. Проверить remote объект: merchant/bot, order ID, сумму в minor units и валюту, фактический статус. UI close/callback клиента и наличие webhook сами по себе не подтверждают оплату.
5. Подтвержденный эффект завершить идемпотентно. Для нового send требуется доказанное отсутствие эффекта **и исключение позднего результата старой попытки**; зафиксировать evidence reference и CAS revision. Иначе оставить unknown для оператора.

Telegram `sendMessage` не имеет общего server-side idempotency key или метода чтения произвольной истории бота. Transactional outbox гарантирует локальное намерение, а не exactly-once доставку Telegram. Нельзя заменять неопределенность слепым повтором или автоматизацией пользовательского MTProto аккаунта.

## Проверка

Проверьте реальный process kill до commit, после business+intent commit, после remote effect до receipt и после receipt до завершения job. После каждого рестарта сравните устойчивый ID и бизнес-состояние. Для lost-response fake transport должен сначала записать эффект в отдельное устойчивое хранилище, а затем потерять ответ: простой mock exception до вызова не воспроизводит это окно.

Не записывайте token, initData, message text или provider credentials в retry reason. Причины — фиксированные коды, контекст — безопасные корреляционные ID. Полные payload/receipts доступны отдельно по ACL и retention проекта.
