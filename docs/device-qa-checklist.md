# Проверка демо Mini App на устройствах перед релизом

Перед каждым тегом `vX.Y.Z`, начиная с 0.25.0, демо Mini App проверяется в настоящем Telegram на iOS, Android, Desktop и Web. Отчет лежит в `docs/device-checks/<версия>/` и входит в тег. Release workflow проверяет отчет (`scripts/device_report.py bundle`), прикладывает к релизу `device-report-<версия>.zip` с отчетом и скриншотами и добавляет таблицу результатов в описание релиза. Без корректного отчета релиз 0.25.0 и новее не публикуется.

Браузерные проверки CI (Lighthouse, axe, Playwright) это не заменяют: они не воспроизводят клавиатуру телефона, интерфейс Telegram, сворачивание и производительность устройства.

## Подготовка (около 10 минут)

1. Тестовое окружение Telegram: отдельный аккаунт на каждом устройстве ([Testing Mini Apps](https://core.telegram.org/bots/webapps#testing-mini-apps)). iOS: 10 раз нажать Settings → Accounts → Login to another account → Test. Telegram Desktop: ☰ Settings → Shift+Alt+правый клик по «Add Account» → Test Server. macOS: 10 раз нажать Settings → Debug Menu. Telegram Web: клиент WebK с параметром тестовых серверов `https://web.telegram.org/k/?test=1`; если вход в тестовое окружение там недоступен, отметьте Web как `blocked` с причиной.
2. В тестовом @BotFather создайте бота (`/newbot`).
3. Из корня репозитория на коммите релиза запустите демо с официальным SDK, доступное в локальной сети:

   ```bash
   npm ci && npm run build
   DEMO_HOST=0.0.0.0 DEMO_TELEGRAM=1 npm run demo
   ```

   В PowerShell: `$env:DEMO_HOST='0.0.0.0'; $env:DEMO_TELEGRAM='1'; npm.cmd run demo`.
4. В тестовом @BotFather: `/mybots` → бот → Bot Settings → Menu Button → адрес `http://<IP компьютера>:4173`. Тестовое окружение принимает HTTP без TLS; основное — нет. Telegram Web сам открыт по HTTPS и не загрузит HTTP-фрейм (mixed content): для проверки Web укажите HTTPS-адрес туннеля к порту 4173 — он подходит и остальным платформам.
5. `python scripts/device_report.py new --version X.Y.Z` создает `docs/device-checks/X.Y.Z/report.json`, где все случаи пока `not-run`.

## Что записать по каждой платформе

`device` (модель или компьютер), `os` (версия ОС, для Web — браузер), `telegram` (клиент и версия из настроек), `launch` (способ запуска, по умолчанию кнопка меню в тестовом окружении). `checked_by` — кто проверял (имя или ник, без e-mail и телефона), `checked_at` — дата.

## Случаи

| ID | Действие | Ожидание |
| --- | --- | --- |
| `cold-launch` | Закрыть Mini App, открыть кнопкой меню | Экран «Запись на консультацию» готов без мерцания и ошибок |
| `theme` | Сменить тему Telegram (светлая/темная) при открытом Mini App | Цвета следуют теме Telegram, текст читается |
| `safe-areas` | Развернуть Mini App во весь экран, повернуть устройство, где возможно | Ничего не прячется под вырезом, статус-баром и нижней полосой |
| `keyboard-form` | Ввести имя и телефон | Клавиатура не закрывает поле и кнопку «Подтвердить запись», прокрутка работает |
| `validation-error` | Ввести телефон `abc` и подтвердить | Ошибка у поля, фокус переходит к нему |
| `back-button` | Системный «назад» (Android), жест или Back Telegram | Mini App закрывается или возвращает назад предсказуемо, без зависания |
| `minimize-resume` | Свернуть Mini App и вернуться | Введенные данные на месте, одно нажатие — одно действие |
| `network-error` | Отметить «Симулировать потерянный ответ сервера», подтвердить, затем «Проверить результат» | Сначала «результат неизвестен», после проверки одна подтвержденная запись |
| `single-submit` | Дважды быстро нажать «Подтвердить запись» | Создается одна запись |
| `window-size` | Desktop и Web: сузить окно; планшет: повернуть | Нет горизонтальной прокрутки, действия доступны |

Статусы: `passed`, `failed` (поведение неверное), `blocked` (проверить нельзя: нет устройства, клиент не поддерживает), `not-run`. Для всего, кроме `passed`, обязательна заметка `note` с причиной и шагами. Статус платформы вычисляется из случаев: все `passed` → `passed`, есть `failed` → `failed`, иначе есть `blocked` → `blocked`, все `not-run` → `not-run`, остальное — `partial`. Скрипт проверки откажет, если статус платформы с ними не совпадает.

## Скриншоты

Для каждой проверенной платформы хотя бы один скриншот, рекомендуется три: экран в светлой теме, в темной и ошибка формы. PNG или JPEG до 2 МиБ, имена латиницей в нижнем регистре (`ios-light.png`), файлы рядом с `report.json` и перечислены в `screenshots` платформы. Перед сохранением закройте имя аккаунта, аватар и номер телефона. Скрипт отклоняет текст отчета с токеном бота, номером телефона или e-mail, но изображения проверяет только по формату и размеру.

## Проверка и релиз

```bash
python scripts/device_report.py check docs/device-checks/X.Y.Z --version X.Y.Z
```

Закоммитьте каталог отчета до создания тега. При публикации тега workflow `Release` выполняет `bundle` по тегу (не по рабочему дереву): `device-report-X.Y.Z.zip` и `device-report-X.Y.Z.md` попадают в файлы релиза, таблица — в его описание. Найденные дефекты остаются в отчете как `failed` с заметкой: отчет фиксирует состояние релиза, а не скрывает его.

Отчет подтверждает поведение конкретной сборки на перечисленных устройствах и клиентах. Он не доказывает работу на других моделях, версиях ОС и Telegram и в основном окружении с HTTPS.
