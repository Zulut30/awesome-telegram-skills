# Защита артефактов выпуска

Пункт 95: передача wheel и tarball должна сохранять проверенные байты, источник
и возможность проверки потребителем. Этот порядок дополняет [выпуск версий](releasing.md).
Он не разрешает публикацию и не заменяет приемку приложения, устройств и платежей.

## Что фиксирует сборка

`python scripts/build_release.py --ref <полный-commit> --output <новый-каталог>`
читает обе версии пакетов из выбранного коммита и экспортирует его через
`git archive`. Незакоммиченные изменения рабочего checkout не попадают в пакеты.
`SOURCE_DATE_EPOCH` берется из времени этого коммита. Побайтовая повторяемость
проверяется двумя сборками с одинаковыми инструментами; другая версия backend
сборки или компилятора требует нового сравнения.

| Файл | Что проверять |
| --- | --- |
| Python wheel | Имя и версия из Python manifest, SHA-256, установленный consumer |
| npm tarball | Имя и версия из npm manifest, SHA-256, ESM/typing/consumer |
| `awesome-telegram-patterns-X.Y.Z.cdx.json` | CycloneDX 1.6, оба артефакта, лицензии manifest и прямые зависимости |
| `SHA256SUMS` | Хеши этих трех файлов; basename без путей, повторов и ссылок |

SBOM хранит объявленные зависимости и ограничения версий. Дополнительные Python
extras отмечены `optional`; обязательные зависимости — `required`. Повторяющееся
имя в extras имеет один `bom-ref` и сохраняет каждое исходное ограничение.
Диапазон версии не становится выдуманной установленной версией. Свойства
`awesome-telegram:inventory-scope` и `awesome-telegram:transitive-dependencies`
явно указывают область: артефакты и объявленные прямые зависимости,
без разрешенного транзитивного графа окружения приложения.

Объявленные npm peers тоже включены: React и Vue предоставляются приложением,
а не обозначают встроенные копии этих фреймворков. Для них сохраняются диапазон,
признак `npm:peer-host-provided` и optional из `peerDependenciesMeta`.
Совпадающие dependency/peer относятся к одному npm `bom-ref`, сохраняя обе роли;
необязательный peer не ослабляет обязательную runtime-зависимость. Одинаковые
имена пакетов PyPI и npm остаются разными PURL.

SDK/extras, которые установил потребитель, нужно отдельно инвентаризировать
для его точного окружения. Этот SBOM не объявляет зависимости свободными от
уязвимостей и не является полным перечнем стороннего ПО production-сервиса.

## Опубликованные байты сохраняются

Повторный Release использует `scripts/release_assets.py`: уже существующий файл
остается только при совпадении размера и SHA-256. Старый asset без поля digest
сначала читается через GitHub API и хешируется. Конфликт обнаруживается до
добавления файлов. Сетевая гонка после проверки завершается отказом загрузки:
`--clobber` не применяется. После частичного сетевого сбоя сначала повторяется
проверка состояния, существующие файлы не заменяются.

Отчеты полной приемки получают имя
`distribution-report-<run-id>-<attempt>.json`. Новый запуск добавляет новый
отчет; прежние URL и SHA-256 в истории приемки продолжают указывать на прежние
байты. Исправление пакета или несовместимый повтор сборки требует новой версии.

## Подпись перед PyPI и npm

Контрольная сумма подтверждает целостность относительно полученного manifest,
но сама по себе не подтверждает автора. Registry workflow дополнительно
проверяет attestation wheel, tarball и SBOM через `gh attestation verify`:

- точный репозиторий и `.github/workflows/release.yml`;
- `refs/tags/<tag>` как источник;
- SHA коммита тега и SHA подписывающего workflow;
- предикат `https://slsa.dev/provenance/v1` и GitHub-hosted runner.

Проверка прекращается при отсутствии или несовпадении доказательства.
Ручная историческая сборка тега, запущенная из `main`, может иметь подпись
контекста `main`: это не доказательство сборки в контексте выбранного тега
и не проходит указанную registry-проверку автоматически. Флаги не ослабляются
ради публикации старого файла.

Долгоживущие registry-токены в workflow не используются. Публикация остается
выключенной, пока владелец отдельно не настроит OIDC trusted publishers,
environments и `PUBLISH_TO_REGISTRIES=true`. Для npm direct publish разрешение
trusted publisher должно допускать `npm publish`; настройка только stage
такого права не дает. Требования текущего npm: CLI от 11.5.1 и Node от 22.14.0;
workflow выбирает npm 11 и Node 24. Автоматическая npm provenance требует
поддерживаемого hosted CI, публичного репозитория и публичного пакета.

Права workflow ограничены задачами: обычные проверки имеют `contents: read`,
подписывающая задача Release получает необходимые права записи release и
attestation; задачи PyPI/npm имеют `id-token: write` для своих environments.
Настройки доступа, имена registry и фактическая публикация не подтверждаются
одним наличием YAML. Отчеты live/device остаются обязательными воротами.

## Проверка потребителем

Сначала получите точные файлы выбранного релиза. В собственном каталоге
проверьте `SHA256SUMS` и подпись с ожидаемыми repo/workflow/tag/commit, затем
устанавливайте проверенный wheel/tarball. Сохраняйте команду, версию `gh`,
вывод проверки и SHA-256. Проверка подписи не доказывает отсутствие вредоносного
кода или production-готовность поведения пакета.

Локальные две сборки и тестовый транспорт загрузки не создают подписанную
GitHub attestation. До реального tag-triggered workflow проверенная подпись
новой версии остается отдельным внешним доказательством; registry-публикация
по-прежнему требует решения владельца.
