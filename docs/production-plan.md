# План выхода Awesome Telegram Skills в production

Составлен 5 ноября 2026 года на основе [аудита](production-readiness.md), [scope 1.0](v1-scope.md), [дорожной карты](internal/library-roadmap-100.md) и [регистра выполнения](internal/v1-progress.json). Это план работ, а не разрешение на публикацию и не отчет о завершении этих работ.

## Цель и исходная точка

Довести библиотеку Python/TypeScript и самостоятельные скиллы до выпуска 1.0 с явно принятым stable-контрактом, работающими сценариями, подтвержденной совместимостью и сопровождением.

На исходной точке аудита в регистре были завершены 30 пунктов: 1–19 и 21–31. Остальные 70 сохраняются в scope. Пакеты имеют версию 0.24.0; все 51 группа компонентов остаются experimental. Повторная локальная приемка прошла 85 этапов, 580 Python-тестов с 3 пропусками, 38 TypeScript-тестов и Chrome. Это полезная база, но она не закрывает реальные устройства, платежи, независимую оценку скиллов или production-пилоты.

Первый пилот можно ограничить конкретными сценариями. Это не отменяет оставшиеся требования к 1.0. Отдельный API получает stable только по собственному контракту и доказательствам; реализованный experimental/reference API не становится stable автоматически.

На этапе приемки **32–40** было завершено **39/100**. [Локальная приемка 0.25.0](internal/delivery-025-acceptance.md) прошла 90 этапов, 715 Python-тестов с тремя пропусками, 61 TypeScript-тест и Chrome.

После [приемки компонентов 0.26.0](internal/local-026-acceptance.md) выполнено **67/100**: дополнительно приняты 41–44, 46–55, 57, 59, 61–65, 71–73, 78, 81, 84 и 85. Точные артефакты прошли 92 этапа, 816 Python-тестов с тремя пропусками, 88 TypeScript-тестов и Chrome; установленный магазин — 24 Python-теста, четыре доменных сценария и 246 проверок Chrome. Повторная матрица CI завершила все 37 конкретных задач на Windows, Linux и macOS. Это учет выполненных требований, а не процент надежности. Все компоненты остаются experimental. [Внешние ресурсы](internal/external-acceptance-availability.md) по ответу владельца отсутствуют; проверки устройств, платежных кабинетов, людей и production-пилота сохраняются открытыми.

## Последовательность и критерии завершения

### 0. Зафиксировать базу и подготовить внешнюю приемку

Пункты исходного плана: новые номера не добавляются; готовится исполнение оставшихся требований.

- Зафиксировать принятые изменения аудита отдельным коммитом. Сохранить команды, среду и hashes проверенных артефактов; отличать исходный код, локальную сборку и выпущенный файл.
- Разобрать ветку `codex/accept-025-ci`: сравнить контракты с актуальной main и переносить только подходящие изменения после review. Не сливать прежнюю архитектуру ради совпадения номера версии.
- Составить перечень API-кандидатов на stable и поддерживаемых сценариев: сервисный бот, групповой бот, магазин с Mini App. Для каждого указать владельца проверки, среду, ограничения и необходимые доказательства.
- Сверить pending-пункты с существующим кодом. Там, где реализация уже есть, определить недостающую приемку, а не писать компонент повторно. Статусы менять только после выполнения исходного требования.
- Начать подготовку пунктов 20, 67, 75–77, 88–90: договориться об участниках, устройствах, отдельных тестовых ботах, HTTPS-среде, доступных платежных контурах и проектах пилота. Не ждать завершения UI, чтобы искать iPhone или участников.
- Зафиксировать матрицу окружений первого релиза по фактической совместимости SDK. Для production не выбирать EOL-окружение; не объявлять новую версию Python/Node поддерживаемой без consumer-прогона. Изменение минимума объявлять явно.

Условие завершения: есть воспроизводимая база, перечень stable-кандидатов и таблица приемки с исполнителями. Отсутствующие внешние ресурсы записаны как зависимости с ответственным; они не помечены пройденными.

### 1. Надежность бота и доставки событий

**Пункты плана:** 32–40.

Порядок реализации: 32 → 33–34 → 35–36 → 37–38; shutdown и наблюдаемость из 39–40 добавляются вместе с этими изменениями.

- Проверять actor, scope, revision и устойчивый operation ID перед эффектом; конкурирующие workers должны разделять одно сохраненное намерение операции.
- Сделать прием webhook с проверкой секрета, ограничением тела и контролируемым разбором Update. Не подтверждать прием до обработки или надежного сохранения; не менять существующий polling/webhook режим незаметно.
- Реализовать durable inbox: повтор события, рестарт и ошибка декодирования не должны терять уже принятое событие. Неизвестный payload сохраняется/изолируется по явной политике и становится наблюдаемой ошибкой.
- Связать бизнес-запись и намерение исходящей отправки транзакцией. Описать границы outbox: потерянный ответ внешнего API может требовать сверки, а не автоматического повтора.
- Разделить retry для чтения, идемпотентной записи и неизвестного исхода. Добавить ограничение попыток, backoff, обработку `retry_after` и маршрут ручной сверки опасных операций.
- Подключить уведомления, отписку и jobs с восстановлением после рестарта. Проверить закрытие сессий, остановку workers, backlog и сохранение незавершенных операций.

Условие завершения: в отдельных процессах проверены двойное нажатие, два workers, повтор update, падение до/после commit, потерянный ответ и повторный запуск. Одна бизнес-операция не превращается в две; принятые события не исчезают. Неизвестный сетевой исход остается различимым и допускает сверку.

### 2. Настоящий backend и полный путь Mini App

**Пункты плана:** 41–50.

Зависит от этапа 1. Начать с 41–44, затем связать запуск и клиентское восстановление 45–50.

- Довести композицию signed launch → session → object ACL → бизнес-операция до переиспользуемого примера через установленный пакет.
- Проверить поврежденную/устаревшую initData, неверный bot/environment, строгий разбор и отзыв сессии. Личность и полномочия на объект проверяются раздельно.
- Согласовать deep links и разные способы запуска; явно разделить Telegram launch, браузерное превью и авторизованную сессию.
- Разделить domain/state/API/frontend; запретить поздним ответам перезаписывать новое состояние и смешивать аккаунты.
- Сохранять pending operation ID отдельно от обычного черновика и его TTL. После reload/timeout получать состояние прежней операции, а не создавать новую.
- Проверить back, theme/viewport changes, закрытие и повторный вход без потери допустимого ввода.

Условие завершения: пользователь проходит операцию от запуска до серверного результата; чужой объект и поддельные данные отклоняются. Reload, повтор клика и потеря ответа не создают вторую запись; другой аккаунт не получает прежние данные.

### 3. Завершить UI Mini Apps

**Пункты плана:** 51–60.

Зависит от контрактов этапа 2; экраны проверяются на настоящем backend, browser mock остается отдельным режимом.

- Согласовать токены, базовые компоненты, навигацию, модальные окна, формы и основные экраны.
- Проверить loading/empty/error/success/disabled, длинные подписи, большие шрифты и обе темы.
- Довести safe areas, viewport и экранную клавиатуру: основное действие видно и достижимо; ввод и позиция экрана не теряются при исправимой ошибке.
- Проверить телефон, landscape, планшет, узкое и широкое Desktop-окно; touch, клавиатуру, focus и доступность.

Условие завершения: ключевые задачи выполняются на целевых размерах и способах ввода; нет обрезанного подтверждения, потерянной формы или недоступного управления. Эталонные экраны просмотрены и приняты, а не только автоматически сохранены.

### 4. Native API, устройства и производительность

**Пункты плана:** 61–70.

Зависит от этапов 2–3. Устройства и тестовые аккаунты готовятся с этапа 0.

- Согласовать capability matrix, типизированные кнопки и необходимые native adapters: popup, QR, invoice, контакт, геолокация, biometrics, storage, sharing и файлы.
- Проверять наличие API, документированную версию, разрешение, отмену и поздний callback. Unsupported не превращать в success; fallback не должен ослаблять доверие.
- Для Telegram Serverless определить границу поддержки. Если добавляется `Serverless.call` в wrapper, синхронизировать официальный индекс, типы, каталог, пример и consumer-проверки; не придумывать минимальную версию. Не переносить существующий Python backend в JavaScript автоматически. Serverless не является обязательным хостингом первого stable-контракта.
- Выполнить device-приемку на Android/iOS, реальном планшете, Desktop и Web с записанными версиями клиентов. Проверить cold start, resume, клавиатуру, обе темы, отказы разрешений и смену аккаунта.
- Добавить visual regression по принятым эталонам. Снять baseline скорости и памяти, затем установить измеримые бюджеты; проверить слабое устройство и плохую сеть.

Условие завершения: принятый device report, воспроизводимые визуальные проверки и измерения производительности. Неподдерживаемая capability имеет проверенный запасной сценарий. Browser viewport checks и физические устройства отражены раздельно.

### 5. Платежи и оплачиваемый доступ

**Пункты плана:** 71–80.

Зависит от надежности, identity/ACL и восстановления операций из этапов 1–2. Выбранный платежный UI зависит от этапов 3–4.

- Зафиксировать допустимые платежные маршруты по типам товаров и актуальным правилам. Реализовать общую модель заказа, оплаты и доступа.
- Принимать платежные события по протоколу конкретного провайдера; сверять серверный заказ, получателя, сумму, валюту и идентификатор платежа.
- Завершить Stars-сценарий и предусмотренные планом адаптеры Crypto Pay, Platega и ЮКассы. Подключать их опционально, без обязательной установки всех провайдеров каждому приложению.
- Реализовать сверку, возвраты, продление/истечение доступа и корректную обработку дублей, перестановки событий и неизвестного исхода.
- Проверить сценарии в разрешенных тестовых контурах. Недоступный sandbox/API или отсутствие нужного доступа сохраняет пункт незавершенным; офлайн-модель не заменяет provider evidence.

Условие завершения: полный order → payment → access → refund/expiry с серверным подтверждением, устойчивым ID и проверками отказов. Клиентское закрытие invoice не выдает доступ. Повтор события не дублирует оплату или выдачу.

### 6. Совместимость, безопасность, поставка и эксплуатация

**Пункты плана:** 81–87, 91–98.

Работа начинается на этапе 0 и сопровождает каждый компонент; здесь принимается ее полный результат.

- Проверять публичные контракты через установленный wheel/tarball и заявленную матрицу ОС/версий. Привязывать результаты к hashes артефактов и сохранять происхождение рецептов.
- Для каждого критического инварианта иметь тест отказа: чужой объект, поддельный launch/receipt, повтор, crash/restart, неизвестный результат, неправильный входящий payload.
- Синхронизировать exports, каталог, changelog, примеры и локальные references скиллов. Проверять нижние границы зависимостей, обновления API и поддерживаемые окружения.
- Проверить лицензии и авторство, канал сообщений об уязвимостях, защищенный выпуск и правила поддержки. Не менять лицензию автоматически.
- Выполнить backup → restore и migration → rollback на копии данных; проверить ротацию секретов, лимиты, алерты, runbooks и назначение ответственного за инциденты.
- Подготовить реальную миграцию потребителя к 1.0. Историческая формулировка пункта 98 упоминает 0.5.0; дополнительно проверить актуальную локально принятую 0.25.0 и форматы сохраненного состояния. Не удалять старые operation IDs для обхода несовместимости.
- До RC реализовать единый release identity: Python `1.0.0rc1` и npm `1.0.0-rc.1` должны правильно проходить manifests, каталоги, CLI, генераторы, имена артефактов и verifiers. Текущий verifier требует числовую версию; одной смены строки на `rc1` недостаточно. Не переиспользовать номер уже выпущенного артефакта.

Условие завершения: обязательный CI и чистые consumers проходят заявленную матрицу, включая Windows/Linux/macOS для принятых обещаний. Артефакты воспроизводимо собираются из выбранного коммита, проверяются и сопровождаются checksum/evidence. В stable scope нет незакрытых критических и высоких дефектов; восстановление и миграция выполнены, а не только описаны.

### 7. Независимая приемка скиллов и удобства

**Пункты плана:** 20, 88–89.

Baseline запускается на этапе 0; финальный повтор — на кандидате после функциональных изменений.

- Независимые исполнители решают задачи выбора скилла и интеграции через публичный API. Включить все фактические 42 скилла: историческое название пункта 88 «41 навык» не должно исключить добавленный навык.
- Добавить новые случаи Serverless, ограничения SDK/Python и сохранения исходного стека. Проверить перенос одного каталога скилла без зависимости от соседних.
- Фиксировать точную модель, режим, hash instructions/descriptions и условия запуска. Использовать существующий gate выбора 95% на согласованных моделях; не переносить старый результат на новые тексты или новые задачи.
- Отдельно измерять полезность полного решения: поддерживаемые API, сохранение архитектуры, права, безопасные эффекты, проверки и ограничения. Цели улучшения/допустимых затруднений принять по baseline до контрольного прогона.
- Провести наблюдаемые задачи с 5–8 разработчиками: установка, первый запуск, поиск рецепта и подключение в существующий проект. Исправления повторно проверить на тех же типах задач без подсказок автора.

Условие завершения: есть независимые отчеты по зафиксированным версиям, выполнены принятые пороги и исправлены критические ошибки решений. Статическая проверка YAML, авторский разбор и оценка другой модели остаются разными свидетельствами.

### 8. Ограниченные production-пилоты

**Пункты плана:** 90.

Начинать после приемки нужного сценария, его безопасности, live/device checks и эксплуатации. Незавершенные функции в пилот не подключаются.

- Выбрать минимум один настоящий бот и один Mini App с согласованными правами и данными.
- До запуска зафиксировать период наблюдения, ожидаемую нагрузку, условия остановки, метрики ошибок/backlog/задержек, восстановление и ответственного за поддержку. Не подбирать критерии задним числом под результат.
- Проверить ошибки пользователей, дубли, рестарт, сетевые сбои, поддержку и фактический путь восстановления. Пилот магазина требует отдельно принятого платежного маршрута.

Условие завершения: период наблюдения закрыт, результаты сопоставлены с заранее заданными критериями, известные дефекты исправлены и повторно проверены. Молчаливое отсутствие жалоб не считается успешным пилотом.

Условие завершения: RC имеет полные доказательства к точным артефактам и принятую таблицу соответствия требованиям 1.0.

## Ближайший пакет работ

Следующий контур — интеграция разработки **0.27.0**: фактические возвраты магазина, надежный polling-прием, отмена/возобновление Stars и обновленный каталог Serverless. Локальные реализации еще требуют общей поставки и приемки; готовый код не меняет статус автоматически.

1. Проверить возврат в установленном магазине через operator ACL, финансовый журнал и восстановление после падения между внешним эффектом, ledger и выдачей доступа.
2. Проверить cancel/resume Stars с сохраненными поколениями команд, упорядочиванием updates и ручной сверкой некоррелируемого неизвестного исхода; оплаченный период не сокращается отменой продления.
3. Принять Serverless в каталоге с неизвестной минимальной версией, точными callback-типами и отказом универсального фасада до нативного вызова.
4. Повторить артефакты, миграции, матрицу CI и отрицательные security-сценарии; завершать доступные требования 81–87 и 91–98 по их собственным доказательствам.
5. Выполнить слепые задачи выбора, переноса и интеграции навыков через публичный API. Человеческие замеры и пилоты остаются отдельными требованиями.

## Правила исполнения и сроки

Для каждого пункта: исходное требование → текущая реализация/пробел → контракт → код и consumer → негативная/отказная приемка → синхронизация документов → evidence → отдельный коммит. Рабочая реализация без обязательной проверки остается pending/in_progress. Повторно подтвержденный существующий код принимается по тем же критериям, без формального переписывания.

Полную поставку запускать после `npm.cmd ci` через `python scripts/verify_pattern_packages.py` с Chrome/CHROME_PATH. Сохранять команду, окружение, версию, hashes и ограничения; не подменять live/device результаты SDK/mock/browser свидетельствами.

Календарный срок пока не назначен: нет измеренной скорости завершения пунктов, подтвержденного графика устройств/людей и всех платежных контуров. После фактического baseline первого использования оценить оставшийся объем отдельно по реализации, автоматическим проверкам и внешней приемке. До этого обещание даты 1.0 будет предположением.

Этот документ задает порядок исполнения, не меняя исходные номера и требования. Канонический статус работы хранится только в `internal/v1-progress.json`; создание этого плана не закрывает ни один pending-пункт.
